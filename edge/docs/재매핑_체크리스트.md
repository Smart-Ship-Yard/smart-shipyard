# 0단계 ★ 바닥 준비

> **왜 추가했나:** 첫 매핑(v1)이 실패한 원인이 매핑 품질이 아니라 **공간 부족**이었다.
> 미탐사 영역을 전부 빈 바닥으로 가정하고 다시 계산해도 결과가 같았으므로,
> 원인은 실제 벽·가구다. **바닥을 안 치우면 몇 번을 다시 떠도 똑같다.**

- [ ] 방에서 **제일 트인 자리**를 고른다
- [ ] 그 자리를 중심으로 **지름 1.2 m 원**(또는 1.2 × 1.2 m 사각형) 안을 완전히 비운다
      → 바닥에 테이프로 표시해두면 확인하기 쉽다

      ℹ️ 1.2 m 는 **폼롤러(약 0.15 × 0.15 m) 기준**이다. 중앙 물체가 커지면
      필요 공터도 커진다. 물체 크기를 알면 미리 계산할 수 있다:

      ```bash
      python3 scripts/check_patrol_space.py --obstacle <가로m> <세로m>
      ```

      **여기서 막히면 매핑을 해도 순찰 원이 안 나온다.** 줄자로 먼저 확인할 것.
- [ ] **중앙 물체를 세워서** 정중앙에 놓는다

      ⚠️ **눕히면 안 된다.** 라이다는 지면 0.20 m 높이의 **평면 하나만** 스캔한다.
      눕힌 폼롤러는 높이가 0.127 m라 그 평면 아래에 있어 **아예 안 잡힌다.**
      맵에도 안 찍히고 주행 중에도 안 보여서 로봇이 밟고 지나간다.
      → 물체 높이가 0.20 m를 넘지 않으면 **받침대를 써서 라이다 높이에 걸치게** 한다.
        받침 높이 = 0.20 − (물체 높이 ÷ 2). 단 **받침은 물체보다 작아야 한다**
        (받침이 더 넓으면 라이다에 안 보이는 부분에 로봇이 부딪힌다).

- [ ] **모형 배가 중앙 물체일 때는 위 받침대 규칙이 통하지 않는다 — 임시 상자를 쓴다**

      위 규칙은 물체 단면이 높이에 관계없이 일정할 때 성립한다. 모형 배는
      아니다. 전체 높이는 라이다 평면을 넘더라도 그 높이에 걸리는 것은
      **마스트뿐이고 선체는 훨씬 아래**에 있다. 마스트는 폭이 몇 cm라 한
      바퀴에 스캔점이 한두 개밖에 안 잡혀 노이즈로 묻힌다.

      배를 통째로 높이는 것도 답이 아니다. **뎁스카메라가 갑판 위 결함을
      봐야 해서** 배 높이는 카메라 높이에 맞춰 이미 정해져 있다.

      → **매핑하는 동안만** 배 자리에 종이상자를 놓는다.

      - 높이 **0.25 m 이상** (라이다 평면 0.20 m 를 확실히 넘게)
      - 바닥 크기는 **배 윤곽 이상**. 조금 큰 편이 여유가 늘어 오히려 낫다
      - 재질은 **종이·판지**. 검은 광택면이나 유리는 적외선을 놓칠 수 있다
      - 바닥에 상자 윤곽을 테이프로 표시 → 매핑 후 상자를 치우고 그 자리에 배를 놓는다

      이러면 맵에 선체 윤곽이 남아 순찰 중심이 자동으로 잡히고,
      글로벌 코스트맵의 `static_layer` 가 그 자리를 장애물로 들고 있어
      Nav2 가 배를 가로지르지 않는다. **시연할 때는 상자가 없다.**

      > 뎁스카메라로 배를 인식해 중심을 측량하는 방식으로 대체할 계획이다.
      > 그때는 상자가 필요 없어진다 — `docs/배_중심좌표_측량_요청.md` 참조.

- [ ] **캘리브레이션 시작점과 1.5 m 끝점, 두 곳에 테이프**를 붙인다

      > **왜:** 캘리브레이션이 성공하면 **로봇이 서 있던 자리가 map 원점 (0,0)**,
      > **직진한 방향이 map +x축**이 된다. 방 구조와 무관하게 로봇 위치가
      > 좌표계를 정의한다. 다음에 이 맵을 재사용하려면 **같은 자리·같은 방향**에서
      > 캘리브레이션해야 한다. 점 하나만 찍으면 방향을 재현할 수 없어서 두 점을 찍는다.
      > 방향이 5°만 틀어져도 2.5 m 떨어진 지점에서 22 cm 어긋난다.

- [ ] **앵커를 고정한다.** 매핑 후 앵커를 옮기면 이 맵은 무효다.

# 필수 사전 지식 ★ 3가지

이걸 모르면 실패해도 실패한 줄 모른다.

### ① `success: True`는 캘리브레이션 성공이 아니다

`/uwb_map_calibration/calibrate` 서비스가 돌려주는 `success: True`는
**"수집을 시작했다"**는 뜻일 뿐이다. 진짜 결과는 로봇이 1.4 m를 지난 뒤
**터미널 1 로그**에 `[캘리브레이션 성공]` / `[캘리브레이션 실패]`로 나온다.
**반드시 그 줄을 눈으로 확인한다.**

### ② 캘리브레이션 노드를 끄면 안 된다

`uwb_map_calibration` 노드가 `map→uwb_frame` TF의 **유일한 발행자**다.
Ctrl+C나 `pkill`로 끄면 TF가 사라지고, `slam_map_alignment`가 UWB 샘플을
전부 버려서 나중에 `align`이 데이터 부족으로 실패한다.
이 노드는 `localization.launch.py` 안에 있으므로 **터미널 1을 건드리지 않는다.**

### ③ 캘리브레이션은 1.4 m를 채우면 자동으로 끝난다

```
최소 1.4 m 이동 시 자동 종료 / 최대 30초 타임아웃
```
1.5 m 직진은 약 10초 걸리므로 여유 있다.

> **2026-08-14 변경:** 이 값은 원래 1.0 m 였다. 1.5 m 를 주행해도 계산이
> 1.0 m 에서 끊겨 실제로는 그보다 짧은 구간만 쓰였고, 짧을수록 각도 오차가
> 급격히 커진다. 종료 판정이 **양 끝점 두 개의 UWB 측정**으로만 이뤄지므로
> 주행거리와 같은 값(1.5)으로 두면 노이즈 때문에 영영 못 넘겨 타임아웃이
> 난다. 그래서 주행 1.5 m / 판정 1.4 m 로 **마진을 둔 한 쌍**이다.
> 둘 중 하나만 바꾸면 안 된다.

### ★ 터미널 1 로그를 확인 — 여기가 진짜 결과

```
[캘리브레이션 성공] 캘리브레이션 완료 #1: theta=XX.XXdeg (uwb->map), travel=1.4Xm, samples=NNN
```

`travel` 이 1.5 가 아니라 **1.4 언저리로 찍히는 것이 정상**이다. 판정 기준이
1.4 m 라 그 지점에서 계산이 끝나고, 로봇만 1.5 m 까지 마저 간다.

실패 시 원인별 조치:

| 로그 | 원인 | 조치 |
|---|---|---|
| `이동거리 부족 (X.XXm < 1.4m)` | 로봇이 안 움직임 | 터미널 2가 떠 있는지 확인 |
| `샘플 부족 (N개)` | UWB 끊김 | 문제해결 **A** |

### ★ 주행 방법 — v1 실패의 직접 원인이었던 부분

> **왜 중요한가:** 중앙 물체 주위를 한 바퀴 완전히 돌지 않으면
> 자유공간이 **고리(ring)를 이루지 못한다.** 그러면 순찰 경로가
> 아예 생성되지 않는다. v1 맵에서 실제로 이 문제가 났다.

- [ ] **중앙 물체 주위를 완전한 한 바퀴 이상** 돈다 ← 가장 중요
- [ ] 반지름을 바꿔가며 **2~3바퀴** (안쪽 한 바퀴, 바깥쪽 한 바퀴)
- [ ] 중앙뿐 아니라 **방 바닥 전체를 훑는다**
      (안 지나간 곳은 미탐사로 남고, 최종적으로 주행 불가 영역이 된다)
- [ ] **천천히** 움직인다 (스캔 매칭이 따라올 시간을 준다)
- [ ] 같은 곳을 다시 지나가 루프 클로저를 유도한다
- [ ] 방향(시계/반시계)은 **아무래도 상관없다.** 양방향으로 돌면 오히려 좋다

중간 확인 (터미널 5):
```bash
ros2 topic hz /map
```
`average rate: 0.5` (2초에 1번)이면 매핑이 정상 동작 중이다.

## 7단계. UWB 맵과 SLAM 맵 좌표 일치 — 터미널 3

```bash
ros2 service call /slam_map_alignment/align std_srvs/srv/Trigger
```

**응답에 진짜 결과가 담겨 있다** (캘리브레이션 서비스와 다르다):

```
Trigger_Response(success=True, message='정합 완료 #1: theta=XX.XXdeg, tx=..., ty=...,
                 대응점=NNN, inlier 비율=XX.X%')
```

| 항목 | 통과 기준 |
|---|---|
| `success` | `True` |
| `대응점` | 10개 이상 (수십~수백이면 좋음) |
| `inlier 비율` | **40% 이상** (70% 넘으면 좋음) |

RViz에서 fixed frame을 `map`으로 했을 때 로봇이 화면 중앙에 있으면 정상.
(로봇 좌표축이 몇 cm씩 떠는 것은 UWB 노이즈로 **정상**이다. 매핑에는 영향 없다.)

## 8단계. 맵 저장 — 레포 안에 바로 저장한다

> ⚠️ **반드시 7단계(align)를 먼저 끝내고 저장할 것.**
> 9단계에서 맵과 정합 기록을 저장 순서로 짝지으므로,
> **저장 → align** 순으로 하면 엉뚱한 정합값이 적용될 수 있다.
> align → 저장 → finalize 를 연달아 하면 문제없다.

```bash
sudo apt install ros-humble-nav2-map-server   # 아직 설치 안 했다면

cd ~/smart-shipyard/edge/ros2_ws/src/ship_ugv_navigation
ros2 run nav2_map_server map_saver_cli -f maps/shipyard_map_<장소>_v<버전번호>
```

> ★ **저장 경로가 슬램 설명서와 다르다.** 맵 폴더가 `edge/docs/maps/` 에서
> `ship_ugv_navigation/maps/` 로 옮겨졌다. ROS2 패키지 안에 있어야
> launch 파일이 `get_package_share_directory`로 경로를 잡을 수 있고,
> 젯슨과 노트북의 홈 경로(`/home/ship_yard` vs `/home/lee`)가 달라도 깨지지 않는다.

### 맵 이름 규칙

```
shipyard_map_<장소>_v<버전번호>
```

> 예: `shipyard_map_JG_room_v2`
> +) 버전번호는 같은 장소에서 여러 번 맵핑했을 때 맵핑한 순서를 기입하면 됨

**장소를 이름에 넣는 이유:** 나중에 맵이 여러 개 쌓였을 때 `v1`, `v2`만
보면 어디를 찍은 것인지 알 수 없다. 장소를 넣으면 파일 이름만 보고 구분된다.
장소는 영문으로 쓴다 (파일 경로·명령어에 들어가므로).

**같은 장소를 다시 찍으면 버전만 올린다.** 다른 장소면 버전은 다시 `v1`부터.

| 상황 | 이름 |
|---|---|
| JG 방 첫 매핑 | `shipyard_map_JG_room_v1` |
| JG 방 재매핑 | `shipyard_map_JG_room_v2` |
| 시연장 첫 매핑 | `shipyard_map_hall_v1` |

## 9단계 ★ 마무리 — 명령 하나

```bash
python3 scripts/finalize_map.py shipyard_map_<장소>_v<버전번호>
```

**이 한 줄이 4가지를 자동으로 처리한다:**

1. **정합·캘리브레이션 기록을 레포로 복사**
   슬램 노드들이 결과 json을 `/tmp`에 저장하는데 `/tmp`는 재부팅 시 삭제된다.
   파일명에 맵 이름을 붙여 저장하므로 다음 매핑 때 덮어쓰이지 않는다.
   (`/tmp`가 지워지면 노드의 번호 카운터가 001부터 다시 시작하기 때문)

2. **맵 `origin`을 map 좌표계로 보정** ← 이게 가장 중요하다

   > **왜 필요한가:** slam_toolbox는 이 프로젝트 규칙상 map_frame을 `slam_map`으로 쓴다.
   > `map_saver_cli`는 TF를 적용하지 않고 `/map` 토픽 값을 **그대로** 파일에 쓰므로
   > **저장된 맵은 `slam_map` 좌표계**다. 반면 Nav2와 EKF는 `map` 좌표계로 동작한다.
   > RViz에서 정상으로 보이는 건 RViz가 TF를 실시간 적용하기 때문이고, 파일엔 반영이 안 된다.
   >
   > **v2 실측: 0.94 m 이동 + 138° 회전 차이.** 보정 안 하면 지도가 138도 돌아간 채로
   > 인식되어 완전히 사용 불가다.
   >
   > 보정은 `align_*.json`의 θ, tx, ty를 yaml `origin`에 합성하는 것이다.
   > `origin`의 세 번째 값이 yaw라서 **이미지를 다시 그릴 필요가 없다.**
   > 공식은 장소·UWB 배치와 무관하게 항상 같고, 바뀌는 건 숫자 세 개뿐이다.

3. **`free_thresh`를 0.196으로 교정**

   > **왜 0.196인가 (튜닝값이 아니라 상수다):**
   > PGM에서 미탐사 픽셀은 205이고 점유확률은 (255−205)/255 = **0.19608**이다.
   > `map_saver_cli`가 쓰는 기본값 0.25로 두면 0.19608 < 0.25 이므로
   > **미탐사 영역이 전부 "자유공간"으로 분류되어 Nav2가 매핑 안 된 곳으로 경로를 뽑는다.**
   > 0.196이면 0.19608 > 0.196 이라 미탐사가 미탐사로 남는다.
   > **방 크기와 무관하게 항상 0.196이다.** 205라는 인코딩이 안 바뀌기 때문.

4. **순찰 가능 여부 검사 + 순찰 설정 파일 자동 생성**
   로봇 실측 footprint로 반지름별 원을 훑어 완주 가능 여부를 판정하고,
   가능하면 **`config/patrol_<맵이름>.yaml` 을 직접 만들어 준다.**

   > **손으로 옮겨 적을 필요가 없다.** 예전에는 출력된 center/radius 를 보고
   > 사람이 파일을 만들었는데, 오타가 나면 로봇이 엉뚱한 원을 돌고 파일을
   > 만드는 걸 잊으면 기본값으로 뜬다. 지금은 스크립트가 직접 쓴다.
   >
   > 자동으로 정해지는 값:
   > - `center_x`, `center_y`, `radius` — 맵 픽셀 검사 결과
   > - `num_waypoints` — 아래 두 제약으로 계산
   >     ① 방향 변화 360/N < 40도 (넘으면 지점마다 제자리 회전이 필요해짐)
   >     ② 지점 간격 ≥ 도달 판정 반경(0.15 m)의 1.5배
   >   둘 다 만족 못 하면 **①을 우선**한다. ① 위반은 좁은 곳에서 아예 못 가는
   >   문제이고, ② 위반은 궤적이 헐거워지는 품질 문제이기 때문이다.
   > - `direction` — `cw` 고정 (카메라가 오른쪽 90도로 대상을 향함)

### 결과 읽는 법

```
✅ 순찰 가능 (여유 충분)          → 그대로 사용, patrol 파일 생성됨
🟡 사용 가능하지만 여유가 빠듯     → 사용 가능, patrol 파일 생성됨
                                    실행할 때 space:=narrow 를 반드시 줄 것
❌ 완주 가능한 반지름이 없다       → patrol 파일을 만들지 않는다
                                    바닥을 더 치우고 재매핑
```

성공하면 이렇게 출력된다:

```
   📝 순찰 설정 생성: config/patrol_<맵이름>.yaml
      center (3.457, 0.543)  radius 0.30  num_waypoints 10
   🧱 keepout 마스크 생성: masks/keepout_<맵이름>.yaml
      금지 영역 0.50 x 0.60 m (대상 외곽 + 여유 0.05 m)
```

**손으로 옮겨 적을 값이 없다.** 실행할 때 `map` 이름만 주면 launch 가
두 파일을 알아서 찾는다.

### ★ 이 경고가 뜨면 반드시 확인할 것

```
====================================================================
⚠️  포위된 장애물이 2개다 — 자동 선택이 맞는지 확인할 것
====================================================================
  [1] 중심 (  -0.88,    0.82)  크기 0.80 x 0.70 m   <-- 선택됨 (가장 큼)
  [2] 중심 (  -0.02,   -0.02)  크기 0.40 x 0.50 m
```

방 한가운데 떠 있는 물건이 둘 이상이면 **가장 큰 것**을 고른다. 그것이
순찰 대상이라는 보장은 없다. 의자를 돌게 될 수도 있다.

엉뚱한 것을 골랐으면 **위 목록에 찍힌 좌표를 그대로 복사해서** 다시 돌린다.
파일을 열어 고칠 일은 없다.

```bash
# [2] 를 원하면 그 줄의 중심 좌표를 그대로
python3 scripts/finalize_map.py <맵이름> --center -0.02 -0.02
```

**정확히 맞출 필요 없다.** 그 좌표에서 가장 가까운 장애물을 지목한 것으로 보고,
순찰 중심은 그 장애물의 **픽셀 무게중심**을 다시 계산해서 쓴다.
즉 좌표는 "어느 것이냐"를 고르는 용도일 뿐이라 대충 줘도 결과가 같다.

<details>
<summary>목록에 아예 없는 대상을 지정하려면 (라이다에 안 잡히는 경우)</summary>

맵에 안 찍힌 대상은 후보 목록에 나오지 않으므로 좌표를 직접 알아내야 한다.


젯슨의 측량 노드가 완성되면 이 값들이 자동으로 들어와 손으로 줄 일이 없어진다.

## ★ 9-1단계. 매핑 종료 — 무엇을 끄고 무엇을 켜둘지

매핑을 마치고 이어서 자율주행을 시연할 때 헷갈리기 쉬운 부분이다.

| launch | 처리 | 이유 |
|---|---|---|
| **터미널 1** `localization.launch.py` | **끄지 않는다** | Nav2가 필요한 TF·센서·`/cmd_vel` 소비자를 전부 제공 |
| **터미널 2** `mapping.launch.py` | **맵 저장 직후 Ctrl+C** | `slam_toolbox`가 `/map`을 계속 발행 → Nav2 `map_server`와 충돌 |

```
localization.launch.py  ├──── 매핑 ────┼──── 자율주행 ────┤   끝까지 켜둠
mapping.launch.py       ├──── 매핑 ────┤                      map_saver_cli 직후 Ctrl+C
navigation.launch.py                   ├──── 자율주행 ────┤
```

**끄는 시점이 "매핑 주행 종료"가 아니라 "`map_saver_cli` 실행 직후"인 이유:**
`map_saver_cli`는 `slam_toolbox`가 발행하는 `/map` 토픽을 구독해서 저장한다.
먼저 끄면 저장할 지도가 없다. 반대로 `finalize_map.py`는 디스크의 파일만 읽으므로
ROS가 필요 없고 언제 실행해도 된다.

상세: [nav2_작업_정리.md](nav2_작업_정리.md) "9. 실행 순서"

# 문제해결

## A. `샘플 부족` — UWB가 안 나옴

```bash
ros2 topic hz /uwb/pose          # 9~10 Hz 나와야 정상
ls -l /dev/uwb_tag /dev/ttyACM*  # udev 심볼릭 링크 살아있나
```
`/uwb/pose`가 안 나오면 USB를 다시 꽂거나 앵커 전원을 확인한다.
앵커가 3개 이상 잡혀야 좌표가 나온다.

## B. `Message Filter dropping message: frame 'laser'` 가 계속 반복

라이다 스캔이 TF로 변환되지 않아 **맵이 아예 안 그려지는 상태**다.
시작 직후 한두 번은 정상이므로 **10초 이상 반복될 때만** 문제로 본다.

```bash
ros2 topic hz /map               # 0.5 Hz 안 나오면 매핑 안 되는 중
ros2 topic hz /scan_filtered     # 라이다가 살아있나
ros2 run tf2_ros tf2_echo base_link laser
```

## C. `'map'<-'uwb_frame' TF 조회 실패`

**가장 위험한 경고.** `slam_map_alignment`가 UWB 샘플을 **전부 버리는 중**이라
나중에 `align`이 데이터 부족으로 실패한다. 경고는 5초에 한 번만 떠서
조용해 보이지만 그동안 계속 버리고 있다.

원인은 거의 항상 **캘리브레이션 노드가 죽은 것**이다 (Ctrl+C 또는 pkill).

```bash
ros2 node list | grep calib               # 노드 살아있나
ros2 run tf2_ros tf2_echo map uwb_frame   # 값이 출력되면 TF 존재
```

죽었으면 새 터미널에서 되살린다 (이 터미널도 끝까지 열어둔다):
```bash
ros2 run uwb_map_calibration calibration_node
```

⚠️ **TF가 없던 동안 주행한 구간은 대응점이 안 쌓였다.**
TF 복구 후 **5단계부터 다시 매핑**할 것 (로컬라이제이션은 살려둔 채로).

## D. `finalize_map.py` 가 정합 기록을 못 찾음

```
❌ 정합 기록을 못 찾았다: /tmp/slam_map_alignment_results/align_*.json
```

7단계(align)를 안 했거나, 젯슨을 재부팅해서 `/tmp`가 지워진 것이다.
align을 다시 호출하면 된다 (매핑 노드가 아직 떠 있어야 한다).

이미 레포에 기록이 있다면:
```bash
python3 scripts/bake_map_origin.py maps/shipyard_map_<장소>_v<버전번호>.yaml \
    --align maps/calibration_records/align_shipyard_map_<장소>_v<버전번호>.json
```

값을 직접 넣을 수도 있다 (`tf2_echo map slam_map` 출력):
```bash
python3 scripts/bake_map_origin.py maps/shipyard_map_<장소>_v<버전번호>.yaml --tf <x> <y> <yaw>
```

## E. `⛔ 중단: 맵 저장보다 나중에 만들어진 정합 기록밖에 없다`

한 번 부팅한 상태에서 맵을 여러 번 뜨면 `/tmp`에 여러 세션의 기록이 쌓인다.
**어느 기록이 어느 맵의 것인지 파일명만으로는 알 수 없으므로**,
`finalize_map.py`는 **"맵 저장 시각 이전의 기록 중 가장 최신"**을 고른다.

```
14:00  align_001 생성 (A방)
14:05  room_A.pgm 저장
14:10  align_002 생성 (B방)      <- 5분 차이밖에 안 남
14:15  room_B.pgm 저장

room_A -> align_001 선택 (14:05 이전 중 최신)  ✅
room_B -> align_002 선택 (14:15 이전 중 최신)  ✅
```

실행하면 후보 목록을 이렇게 보여준다:
```
  맵 저장 시각        08-07 14:05:00  (room_A.pgm)
  정합 기록 목록:
    08-07 14:00:00  [이전]  align_001.json  <-- 선택
    08-07 14:10:00  [이후]  align_002.json
```

**중단되는 경우는 둘뿐이다:**

| 상황 | 의미 | 조치 |
|---|---|---|
| 맵보다 나중 기록만 있음 | 맵 저장 후 align을 다시 호출했거나, 순서가 꼬임 | 값 확인 후 `--force` 또는 `--tf` |
| 고른 기록이 맵보다 30분 이상 앞섬 | 다른 세션의 기록일 수 있음 | 위와 같음 |

중단 시 **아무 파일도 고쳐지지 않는다.** 화면에 뜬 `theta_rad`, `tx`, `ty` 를
9단계에서 받아적은 `tf2_echo map slam_map` 값과 대조해 판단할 것.

| 대조 결과 | 조치 |
|---|---|
| 같다 | `python3 scripts/finalize_map.py <맵이름> --force` |
| 다르다 | `python3 scripts/bake_map_origin.py maps/<맵이름>.yaml --tf <x> <y> <yaw>` |

**예방법: 7단계(align) → 8단계(저장) → 9단계(finalize)를 연달아 한다.**
그러면 후보가 하나뿐이라 헷갈릴 일이 없다.

## F. 이미 잘못된 값으로 보정해버렸을 때

`bake_map_origin.py`는 **원본을 자동 백업**하고 **적용한 값을 파일에 기록**한다.

무엇이 적용됐는지 확인:
```bash
tail -1 maps/shipyard_map_<장소>_v<버전번호>.yaml
# baked: map<-slam_map applied tx=0.9446 ty=0.1026 yaw=2.4119
```

원본으로 되돌리고 올바른 값으로 다시:
```bash
cp maps/shipyard_map_<장소>_v<버전번호>.yaml.orig maps/shipyard_map_<장소>_v<버전번호>.yaml
python3 scripts/bake_map_origin.py maps/shipyard_map_<장소>_v<버전번호>.yaml --tf <x> <y> <yaw>
python3 scripts/check_patrol_space.py --map maps/shipyard_map_<장소>_v<버전번호>.yaml
```

- `.yaml.orig` 는 **최초 한 번만** 생성되므로 몇 번을 잘못해도 진짜 원본이 남아있다.
- 되돌리지 않고 다시 실행하면 "이미 보정된 맵"이라며 거부한다 (이중 적용 방지).
- **`.pgm` 은 어떤 경우에도 수정되지 않는다.** 최악의 경우도 yaml 한 줄 문제다.

# 참고

- **UWB 앵커를 재배치하면** 캘리브레이션과 align을 재실행하고 **맵을 다시 떠야 한다.**
- **저장된 맵을 다음 세션에 재사용하려면** 테이프 표시한 자리·방향에서
  캘리브레이션을 다시 하고, 앵커는 그대로 두어야 한다.
- `align_*.json` / `calib_*.json` 은 **슬램 노드가 스스로 저장하는 기록**이다
  (`_save_result()`). 저장 위치 `/tmp`도 그쪽 코드의 기본값
  (`result_save_dir` 파라미터)이며, 우리는 결과물을 복사해 갈 뿐이다.
  **그쪽 파일을 수정하지 않으므로 PR 충돌 위험이 없다.**
