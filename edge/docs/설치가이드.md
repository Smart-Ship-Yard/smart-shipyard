## 2. 시리얼 장치 고정 (udev)

### 왜 필요한가

IMU와 Arduino Mega가 둘 다 CH340 계열 칩(VID:PID `1a86:7523`)을 써서
VID/PID로 구분이 불가능하고, 리눅스 기본 이름(`/dev/ttyCH341USB0`,
`ttyACM0` 등)은 "몇 번째로 인식됐는가"로 정해져서 부팅/재연결 순서에
따라 서로 뒤바뀔 수 있다. 실제로 `witmotion_ros`가 Mega를 IMU로 착각해
설정 패킷을 쏘고, `wheel_odom_bridge`가 포트를 못 여는 사고가 있었다.

### 해결 — 물리적 USB 포트 경로(KERNELS)로 고정

```bash
edge/scripts/99-robot-serial.rules       # 규칙 파일 (git 관리)
edge/scripts/install_udev_rules.sh       # 설치 스크립트
```

새 Jetson 세팅 시 또는 규칙이 안 먹힐 때:
```bash
cd ~/smart-shipyard/edge/scripts
./install_udev_rules.sh
```

### 현재 고정된 매핑 (2026-08 기준, 포트를 바꾸면 재확인 필요)

| 심볼릭 링크 | 실제 장치 | KERNELS 값 | 물리 포트 |
|---|---|---|---|
| `/dev/imu` | IMU (IM10A) | `1-2.1.3` | Jetson USB-A 포트 |
| `/dev/wheel_mcu` | Arduino Mega | `1-2.4` | Jetson USB-A 포트 |
| `/dev/lidar` | RPLIDAR A1M8 | `1-2.1.1` | Jetson USB-A 포트 |
| `/dev/uwb_tag` | UWB 태그 | `1-2.1.2` | **USB 허브 경유** |

★ **`uwb_tag`는 허브를 거쳐 연결되어 있다.** 이 허브를 다른 허브로
교체하면 물리 경로 자체가 바뀌므로 `KERNELS` 값을 반드시 재확인할 것.

### 포트가 바뀌었을 때 재확인 방법

```bash
ls /dev/ttyCH341USB* /dev/ttyACM*                          # 지금 뭐가 잡히는지
udevadm info -a -n /dev/ttyCH341USB0 | grep "KERNELS==" | head -5
```
`cat /dev/ttyCH341USB0` (baud는 IMU 9600, Mega 115200)로 실제 어느
장치인지 내용 보고 구분한 뒤, `99-robot-serial.rules`의 해당 줄만 수정.

## 3. 알려진 하드웨어 특성 (겪었던 함정들)

### 3-1. CH341(클론) 드라이버의 `in_waiting` 버그

이 드라이버는 `in_waiting`(내부적으로 `TIOCINQ` ioctl)이 **항상 0을
반환**하는 문제가 있다. `wheel_odom_bridge`, `uwb_dwm1001_driver` 둘 다
이 값에 의존하지 않고 짧은 타임아웃(`timeout=0.01~0.2`)으로 바로
`read()`를 시도하는 방식으로 우회되어 있다. **새로 시리얼 읽기 코드를
짤 때 `in_waiting`을 신뢰하지 말 것.**

### 3-2. Arduino 자동 리셋(DTR)

`pyserial`로 포트를 열면 DTR 신호가 토글되며 Arduino가 자동 리셋된다.
부트로더 → 사용자 스케치 실행까지 약 2~3초 걸리는데, 이 시간 안에
통신을 시도하면 조용히 실패한다. `wheel_odom_bridge`는 연결 시각을
기록해두고 `reset_grace_period_s`(기본 3.0초) 동안은 통신을 건너뛰는
논블로킹 방식으로 처리한다 (`time.sleep()`으로 막으면 안 됨 — 그러면
콜백 하나가 executor 전체를 멈춰버림).

### 3-3. 여러 프로세스가 같은 시리얼 포트를 열려고 하면 상태가 꼬임

`avrdude`(펌웨어 업로드), `screen`, `cat`, ROS2 노드가 번갈아 같은
포트를 열고 닫으면 CH341 드라이버 내부 상태가 이상해져서 데이터가 아예
안 들어오는 경우가 있었다. **증상이 이상하면 먼저 `ps aux | grep tty해당포트`로
좀비 프로세스가 있는지 확인하고, 없으면 USB를 물리적으로 뽑았다 꽂는 게
가장 확실한 해결책.**

### 3-4. Arduino 펌웨어 업로드 시 반드시 포트 점유 노드부터 끌 것

`localization.launch.py`가 `/dev/wheel_mcu`를 이미 열고 있으면
`arduino-cli upload`가 `Error: timeout`을 반복한다. 순서:
```bash
# 1) launch 종료 (Ctrl+C)
arduino-cli compile --fqbn arduino:avr:mega ~/smart-shipyard/edge/firmware/wheel_encoder_mcu
arduino-cli upload -p /dev/wheel_mcu --fqbn arduino:avr:mega ~/smart-shipyard/edge/firmware/wheel_encoder_mcu
# 2) launch 재실행
```

### 3-5. ★ 한쪽 모터 폭주 — PID 적분 와인드업 (2026-08-17 실제 발생)

**증상.** 후진 1.55 m → 곧바로 전진 1.5 m 명령을 넣자 **왼쪽 모터만 전속으로
돌았다.** 로봇을 들어올리자(부하가 사라지자) 오히려 **더 빨라졌고**, 내려놓으니
또 돌았다. 배터리를 뽑아 멈췄다.

> **★ 2026-08-17 저녁 추가 — 원인이 확정됐다. 아래 "추정" 문단보다 이쪽이 정확하다.**
>
> 폭주 감지기(아래 대책에서 신설)가 실제로 잡아낸 데이터:
> ```
> 🛑 왼쪽 바퀴가 명령과 반대로 돌고 있다 (0.4초 지속)
>    명령  L=+256  R=+251 tps
>    실측  L=-1350 R=+200 tps
> ```
> **명령은 좌우 균형있게 정상인데 왼쪽만 반대로 5배 속도.** 그리고 눈으로 본
> 바퀴의 실제 회전 방향은 **앞으로**였다. 즉 바퀴는 전진하는데 엔코더가
> 후진으로 보고한 것 — **왼쪽 엔코더 방향 반전**이다.
>
> 이러면 PID 가 스스로 가속한다:
> ```
> 목표 +256, 측정 -1350 -> 오차 +1606 -> 출력 최대
>   -> 더 빨리 전진 -> 엔코더는 더 큰 음수 -> 오차 더 커짐 -> ...
> ```
> 사람이 배터리를 뽑기 전에는 절대 멈추지 않는 양의 피드백 고리다.
>
> **간헐적인 이유:** 바퀴를 띄운 무부하 시험에서는 정상이었다(좌 +307 / 우 +310,
> 불균형 1%). 부하가 걸릴 때만 터진다. 쿼드러처 엔코더는 A·B 두 채널의 위상
> **순서**로 방향을 판단하는데, 한 채널이 접촉 불량이거나 노이즈를 타면
> 고속·고부하에서 순서가 뒤집혀 읽힌다.
>
> **점검 순서 (유력한 것부터)**
> 1. **엔코더 신호선이 모터 전원선과 나란히 묶여 있는가** — 모터 전원선의
>    PWM 대전류 노이즈가 바로 옆 신호선에 유도된다. 부하가 걸릴 때만
>    터지는 증상과 정확히 맞는다. 묶여 있으면 떼어서 따로 배선할 것
> 2. 엔코더 6핀 커넥터 양쪽 끝(모터 쪽·아두이노 쪽) 접촉
> 3. 피복 손상, 회전부에 쓸린 곳
>
> **판별법:** 배터리를 뽑고 손으로 그 바퀴를 **전진 방향**으로 돌리며
> `ros2 topic echo /wheel/raw_ticks` 의 부호를 본다. 음수가 나오면
> 엔코더 방향 반전 확정. (바퀴가 뒤로 돌았다면 그건 모터 배선 극성 문제로
> 원인이 다르다.)

**원인 (초기 추정, 위 확정 내용으로 대체됨).** 아두이노 펌웨어는 바퀴별 PID 로 속도를
제어한다. 바퀴가 걸리거나 미끄러져 목표 속도에 못 미치는 동안 **적분항이
계속 쌓인다.** 적분 제한이 `±2000` 인데 `KI_L = 0.1` 이므로
**적분항만으로 PWM 200/255 (78 %)** 까지 저장될 수 있다.
그 상태에서 부하가 사라지면 저장된 출력이 한꺼번에 터진다.
"들어올렸더니 더 빨라졌다" 가 이 설명과 정확히 맞는다.

로봇은 후방 라이다가 필터로 잘려 있어 **후진할 때 뒤를 전혀 못 본다.**
후진 중 무언가에 걸리는 것이 이 시나리오의 흔한 출발점이다.

| 확인 | 방법 | 결과 |
|---|---|---|
| 좌우 엔코더 | `/wheel/raw_ticks` 보며 손으로 바퀴 회전 | ✅ 둘 다 응답 (+239 / +258) |
| 정지 중 yaw 안정성 | `/odometry/local` 10초 관찰 | ✅ 변동 0.31도 |

| 좌우 균형 | 같은 시험의 엔코더 누적 | ✅ 불균형 1 % |

**응급 조치 — 이런 일이 또 나면**

1. 바퀴가 도는 중이면 **배터리를 뽑는다.** 소프트웨어 정지보다 확실하다
2. 재연결은 **바퀴를 바닥에서 띄운 채로**, `motion_control.launch.py` 는 띄우지 않는다
   (전원만 넣으면 아두이노 워치독 500 ms 가 모터를 꺼두므로 저절로 돌지 않는다)
3. 위 표의 4가지를 순서대로 점검한다

> **★★ 2026-08-17 심야 — 폭주의 전체 구조가 3층으로 밝혀졌다 ★★**
>
> ```
> ① 왼쪽 엔코더 A상에 노이즈로 가짜 엣지 -> 그 순간 B상을 잘못 읽음 -> 방향 오독
>      (모터 전류가 클수록 노이즈가 커진다 -> 부하에서만 터지는 이유)
> ② PID 가 그 거짓값을 없애려고 최대 출력 -> 바퀴가 더 빨라짐 -> 거짓값이 더 커짐
>      (스스로 가속하는 양의 피드백)
> ③ 정지 명령으로도 워치독으로도 멈출 수 없다
>      둘 다 "목표를 0으로" 바꿀 뿐이고 PID 는 계속 돈다.
>      목표 0, 측정 -1250 -> 오차 +1250 -> 비례항만으로 0.4*1250=500 -> PWM 255.
>      게다가 브리지가 0.1초마다 0을 재전송하면 워치독(500ms)이 계속 갱신되어
>      **발동 자체를 못 한다.** 그래서 배터리를 뽑기 전까지 안 멈췄다.
> ```
>
> **①의 원인 — 반쪽 쿼드러처 디코딩**
>
> ```cpp
> void isr_enc_l() {              // A상 상승엣지에서만 인터럽트
>   bool b = digitalRead(PIN_ENC_L_B);   // 그 순간 B를 한 번 읽어 방향 결정
>   if (b) enc_l_count--; else enc_l_count++;
> }
> ```
> A상에 가짜 엣지가 하나만 떠도 그때 읽은 B가 곧 방향이 된다. 노이즈 한 번에
> 부호가 뒤집힌다.
>
> 참고: **좌우 부호가 다른 것(`--` vs `++`)은 정상이다.** 두 모터가 좌우 대칭으로
> 마주보게 달려 있어 전진 시 두 바퀴의 물리적 회전 방향이 반대이기 때문이다
> (모터 배선을 한쪽만 바꿔 끼우고, 엔코더 부호도 그쪽만 반전시킨 것).
> 고장을 덮는 임시방편이 아니라 대칭 장착에 대한 올바른 대응이다.
>
> **덤 — 4장 "왜 CPR이 스펙 1320이 아니라 330인가" 의 답이 여기 있다.**
> A상 **상승엣지만** 세기 때문에 정확히 1/4 (1320 ÷ 4 = 330) 이다.
> 4장에 "감속기 배율 표기 차이로 추정, 원인 미확정" 이라고 적어둔 것의 진짜 이유다.
>
> **③은 고쳤다 (아래 안전장치 + 펌웨어 하드스톱). ①은 남아 있다.**
> ① 의 근본 해결은 A·B 양쪽을 다 쓰는 정식 쿼드러처 디코딩이다. 노이즈로
> 엣지가 하나 튀어도 +1/-1 로 상쇄되어 방향이 통째로 뒤집히지 않는다.
> 다만 카운트가 4배가 되므로 `ticks_per_rev` 를 330 -> 1320 으로 바꾸고
> 4장 절차대로 오도메트리를 재검증해야 한다. **아직 적용하지 않았다.**
> 그때까지는 왼쪽 엔코더 신호선을 모터 전원선에서 최대한 떼어놓는 것이
> 가장 효과적인 완화책이다.

**펌웨어 하드스톱 (2026-08-17 적용, `wheel_encoder_mcu.ino`)**

워치독이 걸리면 **PID 계산을 건너뛰고 PWM 을 직접 0 으로 쓴다.**
센서가 거짓말을 해도 모터는 확실히 멈춘다 — 마지막 방어선이다.

```cpp
if (hard_stop) {                       // 워치독이 켠다
  setMotorPWM(PIN_L_PWM, PIN_L_DIR, 0);   // PID 우회, 직접 0
  setMotorPWM(PIN_R_PWM, PIN_R_DIR, 0);
  return;
}
```

해제는 **"0이 아닌 실제 주행 명령"이 왔을 때만.** `V,0,0` 으로도 풀리게 하면
상위가 0을 재전송하는 동안 즉시 풀려 PID 가 되살아나 또 폭주한다.

ROS 쪽도 짝을 맞췄다 — 폭주로 잠기면 **아무것도 전송하지 않는다.**
0을 계속 보내면 워치독이 갱신되어 하드스톱이 발동하지 못하기 때문이다.

**적용된 소프트웨어 안전장치 4중 (2026-08-17, `wheel_odom_node.py`)**

하드웨어를 고치더라도 이 장치들은 남겨둔다. 정상 주행에서는 아무 영향이 없고
(정격을 넘을 때만 작동), 시연 중 폭주는 되돌릴 수 없기 때문이다.

| ② | heading_hold 회전 상한 | `max_abs_w` ±0.6 rad/s (로봇 정격) |
| ③ | 최종 바퀴속도 상한 | `max_wheel_speed_mps` ±0.30 m/s. **발행자 무관** — Nav2·teleop·복구행동까지 전부 여기를 지난다 |
| ④ | **폭주 감지기** | 명령과 반대 방향 회전이 0.4초 지속되면 즉시 0속도 + **래치** |

④는 자동 해제하지 않는다. 원인이 하드웨어면 저절로 낫지 않고, 조용히
재개하면 같은 폭주를 반복하기 때문이다. 점검 후 사람이 푼다:

```bash
ros2 service call /wheel_odom_bridge/reset_runaway std_srvs/srv/Trigger
```

관련 파라미터: `runaway_guard_enabled`(true), `runaway_grace_s`(0.4),
`runaway_min_cmd_tps`(30), `max_abs_w`(0.6), `max_wheel_speed_mps`(0.30),
`heading_hold_max_error_rad`(30도).

**Nav2 사용 시 heading_hold 자동 해제**

`navigation.launch.py` 가 기동하면서 `ros2 param set` 으로
`enable_heading_hold=false` 를 넣는다. Nav2 는 자기 컨트롤러가 이미 조향을
닫은 루프로 제어하는데, 그 아래 두 번째 제어 루프가 얹히면
① Nav2 의 미세 조향(|w|<0.02)이 통째로 버려지고 ② 두 루프가 서로 싸운다.
teleop·motion_controller 로 쓸 때는 그대로 켜져 있다(캘리브레이션 직진 품질 유지).

**근본 대책 (미적용 — 시연 전 여유 있을 때 할 것)**

`wheel_encoder_mcu.ino` 의 적분 제한을 낮춘다:

```cpp
integral = constrain(integral, -2000.0f, 2000.0f);   // 현재: PWM 200(78%) 저장 가능
integral = constrain(integral,  -600.0f,  600.0f);   // 권장: PWM 60~72(25%) 로 제한
```

600 이면 정상상태 마찰을 이기기엔 충분하면서 폭주 여력은 사라진다.
단 **정상상태 추종 성능이 조금 떨어질 수 있으므로** 바꾼 뒤 직진·회전을
실측 재검증할 것 (4장 재검증 절차). 업로드는 3-4 절차를 따른다.

## 4. 오도메트리 캘리브레이션 (엔코더/모터)

### 최종 확정값

```python
# ship_ugv_localization/launch/localization.launch.py, wheel_odom_node 파라미터
'ticks_per_rev': 330,
'wheel_radius_m': 0.0308,
'track_width_m': 0.2295,
'right_trim': 0.98,
```

### 왜 CPR이 스펙(1320)과 다른가 — 중요, 재현 시 반드시 이 순서로 검증할 것

초기값(`ticks_per_rev=1320`, 모터 라벨 스펙값)으로는 **직진 거리가 명령의
약 3.7~4배로 나오는 심각한 오차**가 있었다. `track_width_m`을 아무리
조정해도 회전은 맞출 수 있었지만 직진은 절대 안 맞았다 — 이건
`track_width`가 회전 계산에만 쓰이고 직진 거리 계산(`wheel_radius`,
`ticks_per_rev`)에는 관여하지 않기 때문. 결국 **UWB로 실측한 이동거리와
명령 거리를 비교**해서 `ticks_per_rev`가 실제로는 1320이 아니라 330
(= 1320/4)이어야 한다는 걸 역산으로 확인했다. **모터를 교체하거나 새로 사면
반드시 이 방식(UWB 기준 실측 이동거리 대조)으로 재검증할 것.**

> **★ 2026-08-17 원인 확정 — 감속기 표기 문제가 아니었다.**
> 펌웨어가 **A상 상승엣지만** 센다 (`attachInterrupt(..., RISING)` 하나뿐).
> 쿼드러처는 A·B 양쪽의 상승·하강을 다 세면 4배가 되므로,
> **1320 ÷ 4 = 330** 이 정확히 맞아떨어진다. 스펙도 실측도 둘 다 옳았고
> 세는 방식이 1/4 이었을 뿐이다.
>
> 이 반쪽 디코딩은 정밀도만 1/4 인 게 아니라 **노이즈에 취약하다** —
> A상에 가짜 엣지가 하나 뜨면 그 순간 읽은 B가 곧 방향이 되어 부호가
> 뒤집힌다. 실제로 이것이 모터 폭주의 1차 원인이었다 (3-5절).
> 정식 쿼드러처로 바꾸면 두 문제가 같이 해결되지만
> `ticks_per_rev` 를 1320 으로 되돌리고 위 재검증 절차를 다시 밟아야 한다.

### 재검증 절차

1. `ros2 topic pub --once /motion/move_distance ... "{data: 0.5}"` 실행
2. **줄자로 실제 이동거리 실측** (motion_controller 자체 판단 로그는
   신뢰하지 말 것 — 오차가 있으면 이 판단 자체가 왜곡되어 있음)
3. `새_ticks_per_rev = 현재값 × (명령거리 / 실측거리)`로 역산
4. 90도, 360도 회전도 각각 명령 vs 실측 비교, `track_width_m` 미세조정

### 좌우 모터 편향 — 3중 보정 구조

한쪽으로 휘는 문제를 다음 3단계로 해결했다. 순서대로 원인이 다르니
증상 위치(출발 순간 / 정상 주행 중 / 정지 직전)로 어느 걸 조정할지
판단할 것.

| 증상 위치 | 원인 | 해결 위치 |
|---|---|---|
| 정상 주행 중 계속 한쪽으로 | 좌우 모터 정상상태 힘 차이 | `wheel_odom_bridge`의 `right_trim` |
| 출발/정지 순간에만 잠깐 | 좌우 모터 가속·감속 반응속도 차이 | Arduino `KP_L`/`KP_R` 분리, 기동감쇠(`STARTUP_DAMP_*`) |
| teleop으로 오래 직진 시 누적되어 크게 휨 | heading_hold 없는 오픈루프 | `keyboard_teleop_node`에 PI 방식 heading_hold 추가 |

`motion_controller_node`는 원래 heading_hold(P만)가 있었고,
`keyboard_teleop_node`는 나중에 I항까지 추가해서 이식함 (P만으로는
지속적인 편향에 정상상태 오차가 남아 계속 틀어진 채로 고정되는 문제가
있었음).

## 5. UWB

### 5-1. 앵커 배치 원칙

- 4개가 한 직선상에 놓이면 삼변측량이 불안정해짐 — 사각형으로 벌릴 것
- 태그가 앵커로 만든 사각형 **안쪽**에 있을 때 정확도 최고
- 앵커 간 거리가 너무 가까우면(1m 내외) auto-positioning 정확도가
  떨어짐 — 최소 3m 이상 권장
- initiator는 공식적으로 "장애물 없이 모든 앵커와 봐야 한다"는 규칙은
  없지만, 실무적으로 비교적 중앙에 두는 게 안전
- 사람/구조물이 태그와의 가시선을 자주 가리지 않게 할 것
  (실측: 옷걸이에 걸린 옷이 앵커 하나를 가리자 `/uwb/pose` 가 10 Hz → 4 Hz 로 떨어졌다)

### 5-1-1. ★ 높이(z) 배치 — 2026-08-17 실측으로 확립한 규칙

> **"앵커는 무조건 천장 근처로" 는 틀렸다.** 이 프로젝트처럼 태그가 낮은
> 로봇 위(0.4 m)에 있으면, 앵커를 전부 높이 달면 오히려 정확도가 망가진다.

**규칙 1 — 태그 높이를 위아래로 감쌀 것**

DWM1001 은 내부적으로 **3D** 삼변측량을 푼다. 앵커가 전부 태그보다 위에 있으면
수직 방향이 잘 안 풀려서, 솔버가 태그 z 를 틀리게 잡고 **그 오차를 x·y 로 떠넘긴다.**
z 가 틀리면 3D 거리에서 수평 거리를 역산하는 값이 앵커마다 다르게 틀어지므로,
좌표가 단순히 밀리는 게 아니라 **뒤틀린다.**

**규칙 2 — 높이는 평면상 대각선끼리 묶을 것**

낮은 앵커끼리 같은 변에 몰리면 "높다/낮다" 와 "그 변에 가깝다" 가 구별되지
않아, z 오차가 그 축(x 또는 y) 으로 그대로 새어나온다.
**낮은 그룹과 높은 그룹의 무게중심이 같은 자리에 오도록** 대각선으로 엇갈리게 둔다.

```
   y=3.15   A4 (-0.56, 1.60 높음)      A3 (3.67, 0.13 낮음)
                        \                  /
                         \    대각선끼리   /     ← 낮은 둘(A1·A3) 이 대각선,
                         /                 \        높은 둘(A2·A4) 도 대각선
                        /                   \
   y=0.00   A1 ( 0.00, 0.10 낮음)      A2 (4.13, 1.37 높음)

            (괄호 안 = x 좌표, z 높이)   ← 2026-08-17 실제로 통과한 배치
```

**실측 근거 (같은 방, 앵커 x·y 는 고정하고 z 만 바꿔가며 측정).
태그 실제 높이는 0.40 m 이고, 태그가 스스로 계산한 z 가 실제와 얼마나
다른지를 기준으로 삼았다:**

| 배치 | 태그 z 추정 | 오차 | `/uwb/pose` |
|---|---|---|---|
| 전부 태그보다 위 (1.10 / 1.20 / 1.56 / 1.60) | 0.98 m | **0.58 m** | 5.3 Hz |
| 낮은 둘을 **같은 변**에 (0.10 / 0.13 / 1.10 / 1.60) | 0.77 m | 0.37 m | 7.6 Hz |
| 낮은 둘을 **대각선**으로 (0.10 / 1.37 / 0.13 / 1.60) | **0.49 m** | **0.09 m** | 8.1 Hz |

첫 번째 배치에서는 캘리브레이션이 실패했다 —
`타임아웃(30초). 이동거리 1.35m < 1.4m`. 로봇은 실제로 1.5 m 를 갔는데
z 오차 때문에 UWB 가 잰 수평 이동이 짧게 나온 것이다. 대각선 배치로 바꾼 뒤 통과했다.

**정리 — 새 장소에서 앵커를 달 때**

1. 태그(로봇 위 UWB) 높이를 먼저 잰다. 지금 장비는 **0.40 m**
2. 그 위아래로 앵커를 나눈다. 예: 낮은 둘 0.10~0.15 m / 높은 둘 1.3~1.6 m
3. 낮은 둘이 **대각선**을 이루게 한다 (같은 벽에 있는 둘은 높이가 서로 달라야 한다)
4. 그룹 안에서의 몇 cm 차이는 아무래도 좋다. 중요한 건 **낮은 그룹 ↔ 높은 그룹 간격**
5. 낮은 앵커는 지면 반사로 QF 가 조금 떨어진다(실측 73~88 → 59~73).
   z 정확도를 얻는 대가로 감수할 만하다

**측정 기준:** 모듈 정중앙을 재면 된다. 안테나와 보드 중심 차이는 2~3 cm 라
무시할 수 있다. **모든 앵커를 같은 기준으로 일관되게** 재는 것이 훨씬 중요하다.
z 는 태그와의 상대 높이가 아니라 **바닥에서 잰 절대 높이**를 넣는다
(x·y 와 같은 좌표계여야 한다).

**우리 코드는 z 를 쓰지 않는다.** `uwb_ros2_publisher.py` 가
`position.z = 0.0` 으로 버리고 EKF 도 `two_d_mode: true` 다.
그런데도 z 를 정확히 넣어야 하는 이유는, **태그 펌웨어가 x·y 를 계산할 때
z 를 쓰기 때문**이다. z 가 틀리면 우리가 받는 x·y 가 이미 틀어져 있다.

### 5-1-2. auto-positioning 보다 실측 입력이 낫다

주변 철제 구조물이 있으면 auto-positioning 결과가 실제 배치와 크게 어긋난다
(실측: 앱이 계산한 앵커 간 거리 2.59 m vs 줄자 실측 1.50 m — 1 m 차이).
앱 자체도 수동 실측 입력을 권장한다.

**auto-positioning 을 쓰든 수동으로 넣든, SAVE 전에 반드시 검산할 것:**
줄자로 앵커 두세 쌍의 직선거리를 재서 앱 좌표로 계산한 값과 비교한다.
**특히 대각선**을 확인한다 — 회전·왜곡 오차는 대각선에서 가장 크게 드러난다.
10~15 cm 이내면 통과, 30 cm 이상 벌어지면 그 쌍을 의심한다
(실측 사례: 두 앵커 사이를 **침대 금속 난간**이 가로막아 다중경로로
거리가 1 m 가까이 부풀려졌다. 앵커를 난간 위로 올려 해결).

### 5-2. 태그 필수 설정 (DRTLS Manager 앱)

| 항목 | 값 | 이유 |
|---|---|---|
| Location Engine | **활성화** | 꺼져 있으면 `POS` 좌표 자체가 안 나옴 |
| Stationary Detection | **비활성화** | 켜져 있으면 로봇이 정지 시 위치 업데이트가 멈춤 |

### 5-3. `uwb_ros2_publisher.py`에서 잡았던 버그 2건

1. **버퍼링 부재**: `splitlines()`로 즉시 잘라버려서, 시리얼 조각이
   중간에 끊겨 오면(긴 `DIST...POS...` 한 줄이 read() 여러 번에 걸쳐
   옴) 영원히 완성된 줄로 합쳐지지 않았다. `\n` 기준 버퍼 누적 방식으로
   수정.
2. **정규식 포맷 불일치**: 코드는 `POS,x,-1.23,y,4.56,...` 라벨 포맷을
   가정했는데 실제 펌웨어 출력은 `POS,0.55,1.19,0.34,68`(라벨 없음)
   이었다. `LEC_POS_RE`를 실측 포맷에 맞게 수정.
3. **`if line.startswith('DIST'): ...; return`** — 실제로는 한 줄에
   `DIST`와 `POS`가 같이 들어있는데 `return`으로 `POS` 파싱을 건너뛰고
   있었음. `return` 제거.

### 5-4. UWB 캘리브레이션(`uwb_map_calibration`) — 종료조건 버그

원래 "5초 고정 시간" 종료 조건이었는데, 로봇 최고속도(0.15m/s)로는
5초 안에 최소 요구 이동거리(1.0m)를 채울 수 없는 **구조적 모순**이
있었다. "시간이 아니라 실제 이동거리(1.0m)가 채워지면 종료, 단
안전장치로 최대 30초 타임아웃"으로 수정함 (`calibration_node.py`의
`_check_collection_done` 참고).

### 5-5. 캘리브레이션 실행 절차

```bash
# localization.launch.py, motion_control.launch.py 둘 다 켜져 있어야 함
ros2 service call /uwb_map_calibration/calibrate std_srvs/srv/Trigger
# 응답 온 직후 바로 (로봇 정면 방향, 최소 1.5m 이상 빈 공간 확보하고):
ros2 topic pub --once /motion/move_distance std_msgs/msg/Float64 "{data: 1.5}"

ros2 run tf2_ros tf2_echo map uwb_frame   # 항등값(0,0,0)이 아닌지 확인
```
결과는 `/tmp/uwb_calibration_results/calib_NNN.json`에 자동 저장됨.
**앵커를 재배치할 때마다 반드시 다시 실행.**

## 6. LiDAR

### 6-1. 각도 필터 — 후방 180도 제거

`laser_filters`의 `LaserScanAngularBoundsFilterInPlace`는 지정한 각도
구간 **안쪽**만 지우는 단순한 로직이라 wrap-around(±180도 경계를
넘는 범위)를 지원하지 않는다. 후방 180도(+90~+180도와 -180~-90도로
두 조각남)를 지우려면 필터 두 개로 나눠야 한다. 상세: `config/laser_filter.yaml`.

### 6-2. `slam_toolbox` 관련 최소/최대 거리 경고

```
minimum laser range setting (0.0 m) exceeds the capabilities of the used Lidar (0.2 m)
```
`slam_toolbox_mapping.yaml`에 `min_laser_range: 0.2`, `max_laser_range: 12.0`을
명시해서 해결.

### 6-3. ★ 근접 사각지대 — 사람이 로봇 주변에 있을 때 지켜야 할 거리

> **한 줄 요약: 로봇 앞 0.5 m 밖에서 가로지를 것. 뒤로는 절대 다가가지 말 것.**

로봇은 "가까이 오면 무조건 멈추는" 장치가 아니다. **너무 가까우면 오히려
아무것도 못 본다.** 설정에서 그렇게 만들어 놨고, 그건 노이즈를 걸러내기
위한 정상적인 선택이다. 다만 사람이 그 사실을 모르면 위험하다.

#### 보이지 않는 영역 (실측/설정값)

| 항목 | 값 | 근거 |
|---|---|---|
| 라이다 장착 위치 | `base_link` 기준 x=+0.195, z=+0.200 m | `tf2_echo base_link laser` |
| footprint 앞끝 | x = +0.332 m | `nav2_params.yaml` local_costmap |
| 스캔 최소 거리 | **0.15 m** | `laser_filter.yaml` range_filter `lower_threshold` |
| 코스트맵 최소 거리 | **0.20 m** | `nav2_params.yaml` `obstacle_min_range` |
| 지워지는 각도 | **정후방 150도** (±75도) | `laser_filter.yaml` angle_filter_back |

이 숫자들을 합치면:

```
        ↑ 전방
   ┌──────────┐   ← footprint 앞끝 (x=0.332)
   │          │   ↕ 0.137 m
   │    ◉     │   ← 라이다 (x=0.195)
   │          │
   └──────────┘

  코스트맵이 장애물로 찍는 최소 거리 = 라이다에서 0.20 m
                                     = 앞 범퍼에서 겨우 0.06 m
```

**앞 범퍼 6 cm 이내에 들어온 물체는 로봇에게 존재하지 않는다.**
발을 갑자기 들이밀면 로봇은 아무것도 못 보고 그대로 민다.

그리고 **정후방 150도는 아예 안 본다.** 라이다가 보는 것은 전방 210도뿐이다.

#### 제동에 필요한 거리

| 항목 | 값 |
|---|---|
| 순찰 속도 | 0.25 m/s |
| 감속 한계 | -0.8 m/s² (`velocity_smoother` max_decel) |
| 순수 제동거리 | v²/2a = **0.039 m** |
| 코스트맵 갱신 지연 | 5 Hz -> 최대 0.2초 -> **0.05 m** |
| 컨트롤러 주기 | 20 Hz -> **0.013 m** |
| **합계** | **약 0.10 m** |

즉 **로봇이 보기만 하면 10 cm 안에 선다.** 문제는 제동 성능이 아니라
**보이느냐**다. 0.20 m 안쪽은 보이지 않으므로 제동거리가 아무리 짧아도 소용없다.

#### 그래서 지켜야 할 규칙

1. **가로지를 때는 로봇 앞 0.5 m 이상 떨어져서.**
   0.20 m 는 "보이기 시작하는" 경계이지 안전거리가 아니다. 사람 걸음(1.2 m/s)이면
   0.2초 사이에 0.24 m 를 이동한다. 0.5 m 는 그 불확실성까지 흡수하는 값이다.
2. **로봇 바로 앞에 서서 "멈추나 보자"를 하지 말 것.** 그게 정확히 사각지대다.
3. **뒤에서 접근하지 말 것.** 정후방 150도는 안 보인다.
   그리고 Nav2 의 `BackUp` 복구 동작이 **15 cm 후진한다**
   (실측 확인, `/cmd_vel` x = -0.05, 0.05 m/s 로 3초).
   막다른 곳에서 빠져나오는 데 유용해서 남겨뒀지만, **후진 중에는 뒤에 있는
   사람·물건을 전혀 인식하지 못하고 그대로 민다.** 로봇 뒤에 서 있지 말 것.
4. **0.20 m 높이 평면 하나만 본다.** 그보다 위로만 튀어나온 것
   (테이블 상판 모서리, 뻗은 팔, 허리 굽힌 사람의 상체)은 보이지 않는다.
   사람이 서 있으면 정강이가 잡히므로 시연 상황에서는 충분하다.

#### 실측 확인 (2026-08-18)

순찰 중인 로봇 앞 0.5 m 지점에 사람이 서 있게 하고 관측:

```
 2~18s   wp=0 고정,  v = 0.0 / 0.025 / -0.05   <- 멈추고 살짝 후진
20~34s   wp 2->4->6->11,  v = 0.25             <- 비키자 즉시 전속 복귀
consecutive_fails = 0 유지
```

정지 자체는 설계대로다.

다만 이때 **너무 오래 걸렸다.** 60초를 지켜봤는데 웨이포인트가 하나도
안 넘어갔다. 원인은 대기가 아니라 **Nav2 복구 루프가 길어서**였다:

    코스트맵 비우기 -> Spin(90도) -> Wait(5초) -> BackUp(15cm 후진)
        위 4개를 number_of_retries="6" 이 한 바퀴 반 -> 90초 넘게 매달림

순찰 노드는 원래 **막힌 웨이포인트를 포기하고 다음으로 건너뛰도록**
설계돼 있다(`patrol_mission_node._on_failure`, 연속 4회 실패해야 BLOCKED).
그런데 BT 가 FAILURE 를 안 돌려주니 그 건너뛰기 로직이 발동을 못 했다.

-> 2026-08-18 수정: `number_of_retries` 6 -> 3, `Wait` 5 -> 3초,
   `goal_timeout_s` 60 -> 30, `inflation_radius` 0.25 -> 0.20.
   한 목표에 매달리는 시간이 90초 -> 20~25초로 줄어, 막히면 곧바로
   다음 웨이포인트로 건너뛴다.

   ⚠️ 처음에는 "retries 를 3 으로 줄이면 RoundRobin 이 BackUp 차례까지
      가지 않으니 후진이 사라진다"고 판단했는데 **틀렸다.** RoundRobin 은
      자식이 **실패하면 같은 틱 안에서 즉시 다음 자식으로 넘어간다**
      (nav2 `round_robin_node.hpp`: "A returns FAILURE so B gets ticked").
      좁은 곳에서 Spin 은 자주 실패하므로("Collision Ahead - Exiting Spin")
          1회차 코스트맵비우기 -> 2회차 Spin 실패 후 즉시 Wait -> 3회차 BackUp
      이 되어 3회 안에 후진에 도달한다. 실측으로 15 cm 후진을 확인했다.
      **후진을 정말 없애려면 XML 에서 `<BackUp>` 줄을 지워야 한다.**
      지금은 운영자 판단으로 남겨두었다(막힌 곳 탈출에 유용하다).

관측된 또 하나: 로봇이 한쪽으로 우회하다가 방향을 바꿔 **왔던 길을 되짚어
반대쪽으로 우회**하는 일이 1~2회 반복됐다(후진이 아니라 전진으로 되돌아감).
이는 NavFn 이 1 Hz 로 재계획하면서 장애물 좌우 두 경로의 비용이 비슷할 때
번갈아 선택하는 것으로, 위험하지는 않고 시간만 낭비한다. 부풀림을 줄이면
한쪽 경로가 확실히 유리해져 덜 흔들리고, 무엇보다 위 수정으로 20~25초 만에
건너뛰므로 흔들릴 시간 자체가 줄어든다.

## 7. 좌표계 구조 (중요 — 헷갈리기 쉬움)

```
map            UWB 앵커 기준 절대 좌표계 (uwb_map_calibration이 매번 uwb_frame과 정합)
 ├─ odom       로봇 켜진 시점 원점, EKF가 계속 갱신 (ekf_local/ekf_global)
 │   └─ base_link
 │        ├─ imu
 │        └─ laser
 ├─ uwb_frame  그날그날의 앵커 배치가 만드는 좌표계 (원점/축 임의)
 └─ slam_map   그날의 SLAM 매핑이 시작한 지점 원점 (slam_map_alignment가 map과 정합)
```

**TF의 최종 권위자는 항상 EKF 하나뿐** (`map→odom`은 `ekf_global`,
`odom→base_link`는 `ekf_local`)이라는 원칙을 지킬 것. `slam_toolbox`는
`publish_tf: false`로 반드시 꺼둬야 하고, `slam_map_alignment`이 계산한
`map↔slam_map`만 정적 TF로 발행한다.

### 7-1. 지도(.pgm) 재사용 시 반드시 알아야 할 것

`map_saver_cli`로 저장하는 지도는 **`slam_map` 좌표계 기준**이며,
`map↔uwb_frame`, `map↔slam_map` 정합값은 **지도 파일 안에 저장되지
않는다.** 즉:
- 지형(벽 모양)이 그대로면 지도 파일은 재사용 가능
- 하지만 UWB 앵커가 재배치되면 `~/calibrate`, `~/align`을 **반드시
  다시** 실행해야 함 — 지도를 재사용해도 이 두 단계는 생략 불가

지도+정합값 저장 위치: `edge/docs/maps/`

## 10. ★ 아무 에러 없이 조용히 실패하는 것들

이 장은 **에러 메시지가 전혀 안 뜨는데 동작만 안 하는** 경우를 모았다.
오늘(2026-08-18) 하루에만 세 번 당했고, 셋 다 원인을 찾는 데 오래 걸렸다.
공통점은 "로그를 봐도 아무 문제가 없어 보인다" 는 것이다.

### 10-1. 서버 "확인" 버튼을 눌러도 로봇이 재개되지 않는다

**증상**

    서버 로그      📮 [중계] event_ack → 젯슨 전달 완료      ← 정상
    젯슨 터미널1   [수신] /server/inbound 로 중계: {...}     ← 정상
    event_gate_node                                          ← 아무 반응 없음
    로봇           계속 정지                                  ← 에러 없음

**원인** — `websocket_client` 의 발행자와 `event_gate_node` 의 구독자가
**서로만** DDS 매칭이 안 된 상태다. 둘 다 개별적으로는 멀쩡하다:

| 발행자 -> 구독자 | 결과 |
|---|---|
| 새 발행자(`ros2 topic pub`) -> `event_gate_node` | 됨 |
| `websocket_client` -> 새 구독자(`ros2 topic echo`) | 됨 |
| **`websocket_client` -> `event_gate_node`** | **안 됨** |

`ros2 topic info /server/inbound --verbose` 로 봐도 양쪽 다 정상으로 보인다
(RELIABLE/VOLATILE 로 호환, 발행자 1 / 구독자 1). **매칭 여부는 안 보인다.**

정황상 `event_gate_node` 가 뜨는 순간 젯슨 CPU 가 포화돼(부하 13/6코어,
`ekf_node: Failed to meet update rate`, `Behavior Tree tick rate exceeded` 가
쏟아지던 때) 디스커버리 패킷이 유실된 것으로 보인다. **증명된 것은 아니다.**
CPU 를 비우고 Nav2 를 다시 띄우자 곧바로 정상 매칭됐다.

**대처**

1. Nav2(터미널 2)만 재시작한다. `event_gate_node` 가 새로 뜨며 재매칭한다.
   터미널 1 을 안 건드리므로 **UWB 캘리브레이션은 유지된다.**
2. 그래도 안 되면 터미널 1 까지 재시작한다 (캘리브레이션 다시 해야 함).
3. 재시작 전에 **CPU 를 먼저 비울 것.** 포화 상태에서 다시 띄우면 같은 일이 반복된다.

**★ 시연 전 반드시 한 번 시험할 것 (30초)**

로봇이 **주행 중일 때** 서버에서 확인 명령을 한 번 쏜다:

```bash
# 서버에서
cd ~/smart-shipyard/backend && venv/bin/python tools/fake_send_event_ack.py
```

젯슨 터미널 2 에 이 줄이 떠야 정상이다:

```
[event_gate_node] 재개 요청(관제 확인 버튼)을 받았으나 이미 주행 중이다
```

주행 중에 쏘는 것이라 **로봇은 아무 반응도 하지 않는다.** 안전하고, 이
로그 한 줄로 "정지했을 때 재개가 될 것인가" 를 미리 확인할 수 있다.
이 줄이 안 뜨면 위 대처를 하고 다시 확인한다.

### 10-2. 터미널이 한 노드의 로그로 도배돼 다른 노드의 경고가 묻힌다

오늘 이것 때문에 **라이다가 죽은 것도, Nav2 브링업이 실패한 것도 놓쳤다.**
런치 화면이 수백 줄씩 흐르면 사람은 못 읽는다.

노드별로 몇 건씩 찍는지 세는 법:

```bash
python3 -u -c "
import rclpy, collections, threading, time
from rclpy.node import Node
from rcl_interfaces.msg import Log
c=collections.Counter(); ex={}
class W(Node):
    def __init__(s):
        super().__init__('logcount')
        s.create_subscription(Log,'/rosout',s.cb,50)
    def cb(s,m): c[m.name]+=1; ex[m.name]=m.msg[:60]
rclpy.init(); n=W()
threading.Thread(target=rclpy.spin,args=(n,),daemon=True).start()
time.sleep(8)
for k,v in c.most_common(8): print(f'{v:4d}건/8초  {k:<24} {ex[k]}')
"
```

정상이면 8초에 5건 안팎이다. 특정 노드가 100건 넘게 찍으면 그 노드를 고친다
(`throttle_duration_sec` 을 준다).

### 10-3. `ros2 param set` 이 "성공" 이라고 뜨는데 노드가 무시한다

노드가 `__init__` 에서 `self.x = self.get_parameter('x').value` 로 값을
**캐시**해두고 다시 안 읽으면, 런타임 변경이 반영되지 않는다.
그런데 `ros2 param set` 은 파라미터 서버에 값이 저장됐으므로
**"Set parameter successful" 을 반환한다.** 성공처럼 보이지만 아무 일도 안 난다.

지금까지 확인된 것:

| 노드 | 파라미터 | 상태 |
|---|---|---|
| `wheel_odom_bridge` | `enable_heading_hold` | 매 콜백 다시 읽도록 수정됨 (반영됨) |
| `yolo_depth_publisher` | `debug_log` | **캐시됨 — 런타임 변경 안 먹음.** 재시작 필요 |

값을 바꿨는데 동작이 안 바뀌면 **그 노드가 값을 캐시하는지부터 확인할 것.**
