# Nav2 작업 정리 — 결정사항 · 미해결 이슈 · 진행 계획

작성: 2026-08-05 · 담당: Nav2(정기) · 브랜치 `sim/nav2-gazebo`

이 문서는 Nav2 작업 착수 전에 정리한 **구조적 결정 + 팀 협의 필요 사항 + 작업 순서**다.
슬램/비전/백엔드 담당자와 공유해서 인터페이스 합의용으로 쓴다.

---

## 0. 한 줄 요약

Nav2 작업의 산출물은 URDF 수정이 아니라 **`nav2_params.yaml` + launch 파일 + 순찰 노드**다.
슬램 담당자 파일(`ship_ugv_localization`)은 **한 글자도 건드리지 않는다.**
시연장이 어디일지 모르므로 **"이 방에 맞춘 Nav2"가 아니라 "맵이 바뀌어도 도는 Nav2"** 를 만든다.

## 1. 확정된 결정사항

### 1-1. TF 발행 주체 — Option A 채택 (슬램 파일 불가침)

**배경.** 로봇의 각 부품 좌표계 간 변환(TF)은 **발행자가 반드시 하나**여야 한다.
같은 변환을 둘이 쏘면 `TF_REPEATED_DATA` 경고 + 센서 데이터 떨림이 발생한다.

같은 일을 하는 두 도구가 있다:

| 도구 | 하는 일 | 현재 쓰는 곳 |
|---|---|---|
| `static_transform_publisher` | 변환 **1개**를 고정값으로 발행. 한 줄에 하나 | 실물 `localization.launch.py` (`base_link→imu`, `base_link→laser`) |
| `robot_state_publisher` | **URDF를 읽어** 그 안의 모든 조인트를 한꺼번에 발행 | 시뮬 / `display.launch.py` |

**문제는 "지금 고장남"이 아니라 "나중에 합칠 때 충돌"이다.** 실물에서 static TF가 이미
`base_link→laser`를 쏘고 있는데 Nav2 launch가 `robot_state_publisher`를 추가로 켜면 이중 발행이 된다.

**결정: Option A — Nav2 launch에서 `robot_state_publisher`를 켜지 않는다.**

근거는 **Nav2가 URDF를 전혀 요구하지 않기 때문**이다. Nav2에 필요한 4가지는 전부 이미 존재한다:

| Nav2 요구사항 | 제공 주체 | 상태 |
|---|---|---|
| `map→odom→base_link` TF | `ekf_global` / `ekf_local` | ✅ 존재 |
| `base_link→laser` TF | `static_transform_publisher` | ✅ 존재 (PR #14에 실측값 반영) |
| `/scan` | rplidar + laser_filters (`/scan_filtered`) | ✅ 존재 |
| `/cmd_vel` 구독자 | `wheel_odom_bridge` | ⚠️ **PR #14 머지 필요** |

로봇 크기는 URDF가 아니라 `nav2_params.yaml`의 `footprint`에 숫자로 직접 적는다.

**실행 방법 (터미널 2개):**
```bash
터미널1: ros2 launch ship_ugv_localization localization.launch.py   # 슬램 담당자 파일, 그대로
터미널2: ros2 launch ship_ugv_navigation navigation.launch.py       # Nav2 담당자 파일
```

**유일한 손해:** RViz에서 로봇 3D 모델이 안 보이고 좌표축만 보인다. 주행에는 영향 없음.

**나중에(선택):** PR #14 머지 후 여유가 생기면, `localization.launch.py`의 static TF 2개를
`robot_state_publisher` 하나로 교체하는 게 더 표준적인 구조다. launch에
`use_robot_state_publisher` 인자를 기본 false로 넣어두어 나중에 스위치만 켜면 되게 한다.

### 1-2. 지도 파일 위치 이동 (완료)

```
edge/docs/maps/                             (이전)
  → edge/ros2_ws/src/ship_ugv_navigation/maps/   (현재)
```

**이유:** ROS2 launch의 표준 경로 조회(`get_package_share_directory`)는 **패키지 안에 있고
install 규칙에 등록된 파일만** 찾는다. `docs/`에 있으면 절대경로를 하드코딩해야 하는데,
노트북(`/home/lee/`)과 젯슨(`/home/jetson/`)의 홈 경로가 달라 그대로 깨진다.

- 슬램 담당자 확인 완료: 위치 이동 무관
- 원 커밋 `cbc996e`는 Nav2 담당자 본인 커밋 — 슬램 산출물 아님
- PR #14는 `edge/docs/`의 설치가이드 md만 수정, `maps/`는 미접촉 → **머지 충돌 없음**
- `git mv` 사용 → git이 rename으로 추적, 히스토리 유지

### 1-3. install 규칙이란 (setup.py)

ROS2는 폴더가 두 벌이다.

```
src/ship_ugv_navigation/maps/맵.yaml                              ← 편집하는 원본
      ↓  colcon build 가 복사
install/ship_ugv_navigation/share/ship_ugv_navigation/maps/맵.yaml ← 실행 시 읽는 것
```

`colcon build`는 **파이썬 코드만 자동 복사**하고 yaml/pgm/launch/world는 복사하지 않는다.
`setup.py`의 `data_files`가 "이것도 복사해라"라는 지시다.

```python
data_files=[
    (os.path.join('share', package_name, 'maps'), glob('maps/*')),   # (설치 위치, 원본 파일들)
]
```

빠뜨리면 **빌드는 성공하는데 실행할 때 "파일 없음"** 이 난다. ROS2 초보 함정 1위.

### 1-4. 이벤트 정지/재개는 2단계로 미룸

**1단계(현재):** 웨이포인트 순찰 + 무한 반복 주행까지만.
**2단계(나중):** 이벤트 감지 시 정지 / 해결 시 재개.

**근거:** 비전 담당자의 웹소켓 작업 미완료. 확인 결과 `websocket_client.py`에
**수신(recv) 코드가 아예 없어** 현재는 `stream_boost`조차 받지 못한다.
지금 만들어도 테스트할 방법이 없다.
"경로 돌기"가 되면 "멈추기"는 쉽게 붙지만, 반대는 성립하지 않는다.

**단, 1단계 순찰 노드에 `/nav/command` 토픽 구독은 미리 뚫어둔다.** 나중에 웹소켓이
완성되면 연결만 하면 되게.

## 2. 시연장 대응 전략 (핵심)

**전제:** 시연장 크기·형태 미정(방 정도 크기 예상). 시연 당일 Gazebo 튜닝 시간 없음.
최종 발표라 "바로 실행되는지"만 검사.

**따라서 맵이 바뀌어도 재튜닝 없이 도는 구조로 만든다.**

| ❌ 시연장에서 망하는 방식 | ✅ 채택 방식 |
|---|---|
| 웨이포인트 좌표를 코드에 하드코딩 | **배 중심(x,y) + 반지름 + 개수** 파라미터로 원을 자동 생성 → 시연장에선 숫자 3개만 변경 |
| 맵 경로를 코드에 박음 | launch 인자로 받음 (`map:=새맵.yaml`) |
| 이 방 크기에 맞춘 코스트맵 | 방 크기 무관한 상대값 (로컬 코스트맵은 로봇 주변만 관찰) |
| world 파일을 시연장에 맞춰 재제작 | **world는 시뮬 튜닝 전용. 시연장에서는 Gazebo를 켜지 않음** |

**시연장 당일 절차 (목표):**
1. 슬램 담당자가 매핑 → 맵 저장
2. `map:=` 인자로 새 맵 지정
3. 배 중심 좌표 + 반지름 파라미터 3개 입력
4. 실행

**좁은 방은 오히려 유리하다.** 좁은 공간 기준으로 맞춘 파라미터는 넓은 곳에서도 돌지만,
반대는 안 된다.

## 3. 미해결 이슈 / 팀 협의 필요

### 🔴 이슈 1. 저장된 지도의 좌표계 (실물 배포 시 반드시 해결)

**증상 예상:** 저장된 맵이 `map`(UWB 절대좌표)이 아니라 `slam_map` 좌표계일 가능성이 높다.
그대로 Nav2에 올리면 벽이 회전·이동된 채로 코스트맵에 박혀, 로봇이 허공을 피하고 진짜 벽에 부딪힌다.

**원인 분석:**
- `slam_toolbox_mapping.yaml`에서 `map_frame: slam_map`으로 리네이밍 (프로젝트 원칙)
- → slam_toolbox가 발행하는 `/map` 토픽은 `slam_map` 좌표계
- → `map_saver_cli`는 **TF를 적용하지 않고** 그 값을 그대로 파일에 기록
- → 저장된 yaml의 `origin`은 `slam_map` 좌표

`~/align` 호출은 `map→slam_map` TF를 **런타임에** 만들어준다. RViz는 그 TF를 실시간 적용해
그리므로 "fixed frame=map에서 로봇이 중앙" 확인은 정상적으로 통과한다.
**화면은 맞았지만 파일에는 반영되지 않는다.**

**정황 증거:** 저장된 `origin: [0.814, -1.14, 0]`의 3번째 값(yaw)이 정확히 `0`.
정합이 반영됐다면 회전각이 들어갔어야 한다.

**해결 절차 (다음 매핑 세션에서 적용):**
맵 yaml의 `origin`은 `[x, y, yaw]`로 **3번째가 회전각**이다. 이미지 재렌더링 없이 숫자만 고치면 된다.

```bash
# 1. align 호출 후, 맵 저장 "직전"에 변환값을 기록
ros2 run tf2_ros tf2_echo map slam_map      # x, y, yaw 3개 값을 받아적을 것

# 2. 맵 저장
ros2 run nav2_map_server map_saver_cli -f <경로>

# 3. 저장된 yaml의 origin에 위 변환을 합성 (Nav2 담당자가 계산)
```

**시뮬 작업은 이 이슈와 무관하다** (시뮬은 좌표계를 전부 자체 통제).
실물 이식 시점에 해결하면 된다.

**참고:** 정합 결과는 `/tmp/slam_map_alignment_results/align_XXX.json`에 저장되지만
`/tmp`는 재부팅 시 삭제되고, 파일은 젯슨에 있다.

#### 예상 오차 크기 — 무시할 수 없는 수준

매핑 설명서의 절차 순서를 보면:
```
1. UWB 캘리브레이션      <- 이 순간 로봇 위치 = map 원점 (0,0)
2. move_distance 1.5     <- 1.5 m 전진
3. mapping.launch.py     <- 이 순간 로봇 위치 = slam_map 원점 (0,0)
```
**두 원점이 약 1.5 m 벌어져 있다.** 3.5 m 방에서 1.5 m 오차는 벽을 뚫고 다니는 수준.

#### 책임 소재와 담당 (팀 합의사항)

**슬램 담당자의 코드 버그가 아니다.** 런타임 정합 설계는 정확하고 RViz 검증도 통과한다.
빠진 것은 "맵을 파일로 저장할 때 그 TF를 파일에 굽는 단계" 하나로, **운영 절차의 빈칸**이다.
슬램 담당자는 맵 파일을 소비할 일이 없어(실시간 TF만 사용) 이 빈칸이 드러나지 않았다.

**→ Nav2 담당(정기)이 처리한다.** 근거:
1. 매핑을 Nav2 담당이 직접 수행한다
2. 수정 대상이 맵 yaml 한 개, 슬램 코드 수정 0줄
3. PR #14가 미머지 상태라 추가 요청을 넣으면 그것까지 지연된다
4. 맵 파일 좌표계를 신경 쓰는 유일한 소비자가 Nav2다

**Nav2 담당이 실제로 하는 일** = `align` 직후 `tf2_echo map slam_map` 값을 기록하고,
저장된 맵 yaml의 `origin` 세 숫자에 그 변환을 합성하는 것. **맵 파일 후처리이며
저장 명령이나 슬램 코드는 건드리지 않는다.**

**슬램 담당자에게는 "발견 사실"을 공유한다** (우리가 무엇을 추가했다가 아니라):

> 설명서대로 `map_saver_cli`로 저장하면 맵 파일이 `map`이 아니라 `slam_map`
> 좌표계로 저장됩니다. `map_saver`는 TF를 적용하지 않고 `/map` 토픽 값을 그대로
> 기록하는데 그 토픽이 `slam_map` 기준이기 때문입니다. RViz에서 정상으로 보이는 것은
> RViz가 TF를 실시간 적용하기 때문이고 파일에는 반영되지 않습니다.
> Nav2 쪽에서 저장 후 yaml `origin`에 `map→slam_map`을 합성해 사용하겠습니다.

**공유 시점: 재매핑 때 경험적으로 확인한 뒤.** 현재는 설정 파일에 근거한 추론이므로,
`tf2_echo map slam_map`이 `[0, 0, 0]`이 아닌 것을 확인하고 나서 전달한다.
만약 `[0, 0, 0]`으로 나오면 이 이슈는 존재하지 않으며 아무 조치도 필요 없다.

#### 참고: 실무와의 차이

UWB(DWM1001 등)는 창고 AMR·건설현장에서 실제로 쓰인다. 다만 **쓰는 방향이 반대**다.

| | 일반적 실무 | 이 프로젝트 |
|---|---|---|
| `map` 프레임 정의 주체 | 저장된 SLAM 맵 (한 번 만들면 고정) | UWB 캘리브레이션 (매 세션 재정의) |
| UWB의 역할 | 글로벌 EKF에 들어가는 센서 하나 | 좌표계의 기준 |
| 앵커 위치 | 맵 좌표계로 측량해 고정 | 매일 재배치를 전제 |

실무는 "맵이 기준"이고 UWB가 거기 맞춰진다. 이 프로젝트는 "UWB가 기준"이라
맵이 매 세션 UWB에 맞춰져야 하고, 그 대가로 **저장된 맵이 세션에 종속**된다.
"앵커가 매일 재배치된다"는 전제에서는 합리적인 선택이며, 설계 오류가 아니다.

### 🔴 이슈 1-B. JG방 맵으로는 원형 순찰이 불가능 (2026-08-05 실측 분석)

`shipyard_map_v1_JG_room` 을 픽셀 단위로 분석한 결과:

| 항목 | 값 |
|---|---|
| 맵 전체 | 3.55 × 3.40 m = 12.07 m² |
| **실제로 탐사된 자유공간** | **3.99 m² (33%)** |
| 미탐사(205) | 2697셀 = 6.74 m² (56%) |
| 자유공간에 완전히 포위된 장애물 | 1개 — map (2.81, 1.14), 0.35 × 0.40 m |

**⚠️ 위 0.35 × 0.40 m는 실제 레고 배가 아니라 매핑 당시 세워둔 대체용 박스다.**
실제 레고 배 치수는 아직 미확보(다른 팀원 보관). **재매핑 전까지 실측치를 받을 것** —
그 숫자로 치워야 할 공터 크기와 최종 순찰 반지름이 정해진다.
| 그 주위 완주 가능 반지름 | **0.35 m 하나뿐, 안전여유 0 cm** |

**원인.** 로봇이 반지름 R 원을 돌면 차체가 **폭 0.28 m의 띠**를 쓸고 지나간다.
`base_link`가 뒷바퀴 축이라 앞으로 0.332 m 튀어나오기 때문이다.
R = 0.40 m로 돌면 배 중심 기준 **0.31 ~ 0.59 m 구간을 전부 점유**하는데,
이 맵의 자유공간 고리는 그보다 좁다.

**방 크기 문제가 아니다.** 3.55 × 3.40 m면 충분하다. 12 m² 중 4 m²만 매핑됐고
그 4 m²가 대각선 띠 모양이라 배 주위가 뚫리지 않은 것이 원인이다.

### ✅ v2 재매핑 완료 (2026-08-06) — 순찰 가능

`shipyard_map_v2` 로 해결됨. 폼롤러(⌀12.7 세움)를 중앙에 두고 재매핑.

| 항목 | 값 |
|---|---|
| 맵 크기 | 69 × 46 셀 = 3.45 × 2.30 m |
| 탐사 자유공간 | 4.09 m² (52%) — v1의 33%에서 개선 |
| **순찰 중심** | **map (3.46, 0.54)** |
| **순찰 반지름** | **0.30 m** (가용 범위 0.25~0.40) |
| 여유 | 0.075 ~ 0.125 m, **원 전체에 균일** |
| 정합 품질 | 대응점 65개, inlier 60% |
| 캘리브레이션 | 성공 (θ=−57.7°, 1.16 m 주행, 42 샘플) |

**여유가 균일하다 = 안쪽(롤러)과 바깥쪽(벽)이 동시에 조이는 구조.**
한 지점만 치워서 개선되지 않으며, 사방을 5~10 cm씩 넓혀야 한다.
0.075 m는 좁지만 사용 가능 — 로컬 코스트맵이 라이다로 실시간 회피하므로
UWB 오차(±15 cm)와 무관하게 충돌하지 않는다. `inflation_radius`를 0.10 m로 낮출 것.

#### ★ map→slam_map 보정 실제 적용 결과

가설이 실측으로 확인됐다. `tf2_echo map slam_map` 값:

```
Translation: [0.9446, 0.1026]   yaw: 2.4119 rad = 138.19°
```

**0.94 m 이동 + 138° 회전.** 보정 없이 썼다면 지도가 138도 돌아간 채로 인식되어
완전히 사용 불가였다. yaml `origin` 보정:

```
저장값 (slam_map): [-1.15,  -0.533, 0]
보정값 (map)     : [ 2.1571, -0.2667, 2.4119]   ← 실제 적용
```

계산식 (`origin`의 세 번째 값이 yaw라는 점을 이용, 이미지 재렌더링 불필요):
```
new_x   = tx + cos(θ)·ox − sin(θ)·oy
new_y   = ty + sin(θ)·ox + cos(θ)·oy
new_yaw = θ + oyaw
```

**→ 이 절차는 맵을 새로 뜰 때마다 반복해야 한다.** [재매핑 체크리스트](재매핑_체크리스트.md) 9단계 참조.

#### (참고) v1 맵 분석: 좁은 원인이 "미탐사"인가 "실제 장애물"인가

미탐사 영역을 전부 빈 바닥으로 가정하고 같은 검사를 다시 돌려 비교했다.

| 반지름 | [A] 미탐사=주행불가 | [B] 미탐사=빈 바닥 가정 |
|---|---|---|
| 0.30 m | 14개 각도 충돌 | 14개 각도 충돌 |
| 0.35 m | 1개 각도 충돌 | 1개 각도 충돌 |
| 0.40 m | 16개 각도 충돌 | 16개 각도 충돌 |
| 0.50 m | 66개 각도 충돌 | 66개 각도 충돌 |

**두 결과가 완전히 동일하다.** 막고 있는 것은 미탐사 영역이 아니라 **실제 벽·가구**다.
→ **더 꼼꼼히 매핑해도 공간은 넓어지지 않는다. 물건을 물리적으로 치워야 한다.**

#### 가장 유망한 위치

방 전체에서 사방 여유가 가장 큰 지점은 **map (1.71, 0.61), 여유 0.532 m**다.
폼롤러(⌀12.7 세움) 기준 필요값이 0.60 m이므로 **부족분은 약 7 cm**.
현재 박스가 있는 (2.82, 1.15)가 아니라 **이쪽으로 중앙 물체를 옮기고
반경 0.60 m(지름 1.2 m)를 확보**하는 것이 가장 적은 노력으로 되는 방법이다.

#### 재매핑 요구 사양 (시연장에도 동일 적용)

순찰 반지름 R일 때 차체 점유 범위:
```
안쪽 = R - 0.089 m
바깥 = sqrt((R + 0.089)² + 0.332²) m
```
안팎 15 cm 여유 기준으로:

> **배 중심에서 사방 0.85 m 이상이 자유공간이어야 한다.**
> 즉 배를 중심으로 **최소 1.7 × 1.7 m의 트인 공간**이 필요하고,
> 그 영역이 **매핑에서 전부 탐사돼야 한다** (미탐사로 남으면 소용없음).

#### 중앙 물체별 필요 공터 (`scripts/check_patrol_space.py` 계산 결과)

| 중앙 물체 | 물체 반경 | 권장 순찰 반지름 | **치워야 할 공터** |
|---|---|---|---|
| 레고 배 0.35 × 0.40 | 0.266 m | 0.45 m | **1.47 × 1.47 m** |
| 폼롤러 ⌀12.7 (세움) | 0.090 m | 0.28 m | **1.19 × 1.19 m** |

**폼롤러는 반드시 세워서 쓴다.** 눕히면 높이가 0.127 m라 **라이다 장착고(0.20 m)
아래**가 되어 스캔에 전혀 잡히지 않는다. 맵에도 안 찍히고 주행 중에도 안 보여서
로봇이 그대로 밟고 지나간다. 세우면 높이 0.60 m로 확실히 잡히고 바닥 점유 면적도 최소다.

**용도 분리**
- **Nav2 개발/튜닝**: 폼롤러로 충분. 라이다는 물체 모양에 관심이 없다.
- **최종 시연**: 실제 레고 배 필요. 비전이 `block_level` / `ship_defect`를 인식해야 함.
  → 최종 순찰 반지름은 **레고 배 실측 크기**로 다시 계산할 것.

#### 재매핑 시 체크리스트
1. 바닥에 **1.5 × 1.5 m 정사각형**을 테이프로 표시하고 그 안을 완전히 비운다
   (폼롤러만 쓸 거면 1.2 × 1.2 m)
2. 물체를 정중앙에 놓는다
3. 물체 주위를 **완전한 한 바퀴** 이상 주행하며 매핑 (반쯤 돌다 말면 고리가 안 닫혀
   순찰 경로가 아예 생성되지 않는다)
4. 저장 후 `free_thresh`를 0.196으로 수정
5. `python3 scripts/check_patrol_space.py --map <맵.yaml>` 으로 검증
   → "✅ 순찰 가능"과 함께 patrol 노드에 넣을 파라미터가 출력된다

**현 시점 대응.** JG방 맵은 **장애물 회피 동작 확인용**으로만 유지하고,
순찰 파라미터 튜닝은 `scripts/make_demo_world.py`가 생성하는

### 🔴 이슈 1-C. 맵 yaml의 `free_thresh` 버그 (수정 완료)

`map_saver_cli` 기본값 `free_thresh: 0.25`를 쓰면 **미탐사 픽셀(205)이
자유공간으로 분류된다.** (p = (255−205)/255 = 0.19608 < 0.25 → free)

JG방 맵은 56%가 미탐사인데 그게 전부 주행 가능 영역으로 둔갑해,
**Nav2가 매핑되지 않은 영역으로 경로를 뽑고 로봇이 실제 벽으로 돌진**한다.

→ `free_thresh: 0.196`으로 수정 완료. 0.19608 < 0.196이 거짓이 되어 미탐사가 유지된다.
ROS 표준 맵들이 0.196을 쓰는 이유가 정확히 이것이다.

**⚠️ 앞으로 맵을 저장할 때마다 이 값을 확인할 것.** `map_saver_cli`는 매번 0.25로 쓴다.

### 🔴 이슈 2. UWB 캘리브레이션 원점 재현성

`calibration_node.py`는 **"직진 시작 지점을 map 원점 (0,0)으로 정의"** 하는 규약을 쓴다.
매 세션 로봇을 **똑같은 물리적 지점에, 똑같은 방향으로** 놓고 캘리브레이션해야
저장된 지도 위 웨이포인트 좌표가 맞는다. 어긋나면 **모든 웨이포인트가 통째로 밀린다.**

→ 시연 당일 기준점을 바닥에 테이프로 표시할 것.

## 4. 이벤트 정지/재개 설계 (2단계, 참고용)

> **정지는 로봇 혼자서 즉시. 재개는 사람이 백엔드를 통해서.**

- **정지를 로컬로 하는 이유:** 감지→서버→판단→명령 왕복은 지연이 붙고, 와이파이가 끊기면
  로봇이 영영 멈추지 않는다. 안전 로직은 무조건 로컬.
- **재개에 백엔드가 필요한 이유:** "이벤트가 해결됐다"는 판단은 로봇이 못 한다.
  쓰러진 사람이 일어났는지 YOLO는 알 수 없다(안 보인다고 해결된 게 아니라 카메라가
  딴 데 보고 있을 수도). **사람이 프론트에서 "처리 완료"를 눌러야** 한다.

```
[YOLO 감지] ──ROS 토픽──> [순찰 노드]  ← 즉시 정지 (로컬, 지연 0)
                              │
                              └─> websocket_client ──> 백엔드 ──> 프론트 (알림)
                                                                    │
[순찰 노드] <──ROS 토픽── websocket_client <── 백엔드 <── 관리자 "처리 완료"
     └─> 주행 재개
```

**정지 방법 선택:**

| 방법 | 평가 |
|---|---|
| `/cmd_vel`에 0 덮어쓰기 | ❌ Nav2가 "진행 없음"으로 판단 → **복구 행동(제자리 회전/후진) 발동.** 좁은 방에서 위험 |
| lifecycle deactivate | ❌ 과함, 재개가 느림 |
| **`cancelTask()` + 0속도 발행** | ✅ 채택. `nav2_simple_commander` 표준 방법 |

**기존 3중 안전장치 활용:** `wheel_odom_bridge` cmd_vel 0.5초 타임아웃,
아두이노 펌웨어 500ms 워치독 → 순찰 노드가 죽어도 0.5초 안에 정지.

**시연 폴백 (필수 준비):** 백엔드 연동 실패 시 수동 재개 가능하게.
```bash
ros2 topic pub --once /nav/command std_msgs/msg/String "{data: resume}"
```

## 6. 파라미터 선택 (좁은 방 + 원형 순회)

| 항목 | 선택 | 이유 |
|---|---|---|
| Controller | **Regulated Pure Pursuit** | 원 궤도 추종이 부드럽고 파라미터가 적음. DWB는 좁은 공간에서 튜닝 난이도 급상승 |
| Planner | **NavFn** | 3.5 m 방에 Smac Hybrid는 과함 |
| `max_vel_x` | 0.15 m/s | `motion_controller`와 동일하게 시작 |
| `max_vel_theta` | 0.6 rad/s | 위와 동일 |
| `inflation_radius` | 0.25~0.3 | 기본 0.55는 이 방에서 통로를 통째로 막음 |
| local_costmap 크기 | 2 × 2 m | 기본 5 × 5는 맵보다 큼 |
| 복구 행동 | `spin` 비활성, `backup` 거리 축소 | 좁은 공간에서 제자리 회전은 벽을 긁음 |

### 시뮬 로컬라이제이션 (AMCL 문제)

실물은 AMCL을 쓰지 않고 **EKF가 `map→odom`을 제공**한다. 시뮬에서 Nav2 기본 구성대로
AMCL을 쓰면 구조가 달라져 이식이 어긋난다.

**2단계 접근:**
1. **초반:** AMCL로 빠르게 굴러가게 만들어 planner/controller/costmap 튜닝
   (이 파라미터들은 그대로 이식 가능)
2. **최종 검증:** AMCL을 끄고, Gazebo 참값을 `map→odom` TF로 발행하는
   **가짜 글로벌 로컬라이제이션 노드**로 교체해 실물 구조를 그대로 재현

프로젝트에 이미 `dev_tools/fake_sensor_publisher.py`, `fake_slam_publisher.py` 등
가짜 노드로 스택을 검증하는 패턴이 자리잡혀 있어 같은 방식을 따른다.

### Step 6: `patrol_mission_node.py` — 왜 필요한가

**Nav2는 "실행하면 돌아다니는 프로그램"이 아니다.** "여기로 가"라고 지시하면
거기까지 가고 멈추는 엔진이며, 순찰·반복·웨이포인트 순회 개념이 없다.
목표를 하나씩 계속 주는 주체가 반드시 따로 있어야 한다.

```
patrol_mission_node  ──goToPose()──>  Nav2 스택  ──/cmd_vel──>  wheel_odom_bridge
   (운전자)                            (자동차)
```

- 원 위의 웨이포인트 N개(12개 권장)를 순서대로 `goToPose()`
- 마지막까지 가면 처음으로 되돌아가 무한 순회
- `/event/active` 를 구독해 `cancelTask()` / 재개
- 구현: `nav2_simple_commander`의 `BasicNavigator`
  (`goToPose` / `isTaskComplete` / `cancelTask`)

주요 파라미터 (검사 스크립트가 출력하는 값을 그대로 사용):
```yaml
center_x: 3.457      # check_patrol_space.py 출력
center_y: 0.543
radius:   0.30
num_waypoints: 12    # 12개면 경로가 중심에서 0.97R 이상 떨어져 배를 안 스침
direction: cw        # 시계방향 = 카메라(오른쪽 90도)가 배를 향함
```

### Step 7: `event_gate_node.py` — 이벤트 정지/재개

**서버를 경유하지 않고 젯슨 내부에서 완결한다** (2026-08-07 팀 결정).
`websocket_client.py`(비전 담당자 파일)는 **수정하지 않는다.**
같은 토픽을 별도 노드가 구독하는 방식이라 결합이 없다.

```
/event_detection/uvd  (욜로 감지 결과, JSON String)
        │
        ├──> websocket_client.py   ──> 서버      (기존, 미수정)
        └──> event_gate_node.py    ──> /event/active (std_msgs/Bool)
                                            └──> patrol_mission_node
```

```yaml
event_gate_node:
  trigger_classes: [fallen_person, fire, no_helmet]   # ship_defect는 선택
  min_confidence: 0.5
  detect_hold_s: 1.0    # 1초 연속 감지 -> 정지 (안전은 빨라야 함)
  clear_hold_s:  7.0    # 7초 연속 미감지 -> 재개
```

**히스테리시스(감지/해제 기준을 다르게 둠)를 쓰는 이유:** 잘못된 "해결" 판정은
잘못된 "감지"보다 훨씬 나쁘다. 화재가 진행 중인데 로봇이 자리를 뜨면
관제실이 현장을 못 본다. 반면 오탐으로 잠깐 멈추는 것은 손해가 적다.

**`clear_hold_s`가 최소 정지 시간 역할도 겸한다.** 감지 직후 소품을 치워도
그때부터 7초를 세므로 최소 7초는 정지 상태가 유지된다. 별도 파라미터 불필요.

**값 확정은 리허설에서:** 소품을 정리하고 카메라 프레임 밖으로 나가기까지
스톱워치로 재고 +3초. 너무 짧으면(사람이 아직 옆에 있는데 출발) 고장처럼
보이므로, 애매하면 긴 쪽을 택한다.

### 🔴 Step 7 선결 과제 — 이벤트 "지속 여부" 신호가 없다 (2026-08-07 발견)

`yolo_depth_publisher.py`는 **추적 ID 기준으로 객체당 1번만 발행**한다
([yolo_depth_publisher.py:255](../ros2_ws/src/ship_ugv_perception/ship_ugv_perception/yolo_depth_publisher.py#L255)):

```python
if track_id in self.reported_tids:
    continue                      # 이미 보고한 추적 ID면 발행 안 함
self.reported_tids.add(track_id)
publish_ok = True                 # 처음 본 객체일 때만 발행
```

즉 `/event_detection/uvd`는 **엣지 트리거**다. 불이 계속 타고 있어도 메시지는
처음 1번뿐이므로 **"아직 진행 중인가"를 알 수 없다.**

- 정지는 가능 (메시지 1개 = 정지 신호)
- **재개 판단은 불가능** — 이벤트가 남아있어도 조용하고, 해결돼도 조용하다

**→ 비전 담당자에게 연속 신호 토픽 추가를 요청한다 (선택된 방안 B):**

```
/event_detection/present   (std_msgs/String, 추론 주기 0.1초마다)
    ["fire", "fallen_person"]   현재 보이는 위험 클래스 목록
    ["fallen_person"]           화재만 해결됨
    []                          전부 해결
```

- `reported_tids` 필터를 **거치지 않은** 매 프레임 상태여야 한다
- 기존 서버 전송 경로·중복 제거는 **그대로 두고 토픽만 추가**하면 된다
- Bool이 아니라 **클래스 목록**으로 받는 이유: 동시 다발 이벤트 처리와 로그에 필요

**동시 다발 이벤트 처리 (필수 요구사항):**
화재와 낙상이 동시에 잡혔다가 화재만 해결되면 **낙상이 남아있으므로 계속 정지**해야 한다.
그래서 타이머를 클래스별로 두지 않고 **"목록 전체가 빌 때"만** 돌린다.

```
목록이 비어있지 않음  -> 타이머 리셋, 정지 유지
목록이 비었음         -> clear_hold_s 카운트 시작 -> 계속 비어있으면 재개
```

**폴백 (요청이 거절되거나 시간이 없을 때):** 이벤트 수신 시 고정 N초 정지 후 자동 재개.
우리 노드만으로 구현 가능하지만 "해결 감지"는 아니다.

---

⚠️ **참고 — 비전 쪽 "3초"는 위험 이벤트용이 아니다.** 코드 확인 결과:
- `fallback_confirm_frames: 3` = 3**프레임** ≈ 0.3초 (추론 주기 0.1초)
- `block_level_stability_s: 3.0` = 3**초**, **조립단계 전용**
- `_handle_danger_event()` = **시간 조건 없음.** conf 0.5 넘으면 즉시 전송

다만 상위의 `yolo_depth_publisher`가 추적 ID로 이미 1번으로 줄이므로
**서버로 중복 전송되는 문제는 없다** (실기 테스트로 확인됨).
