## 1. 위치 표기 규칙

가장 가까운 구획을 기준으로 **앞뒤·좌우 중 하나**로 표기한다.
정확한 좌표가 아니라 사람이 한눈에 방향을 잡을 수 있는 수준이면 된다.

| 핑의 위치 | 표기 | 예 |
|---|---|---|
| 배의 앞뒤 범위 **안** | 구획 + 좌/우 | `S3 왼편` |
| 배의 앞뒤 끝을 **넘어감** | 구획 + 앞/뒤 + 좌/우 | `S1 앞쪽 왼편` |

- 앞뒤 끝을 넘어가는 경우는 사실상 **S1(선수) 또는 S5(선미)** 뿐이다
- 좌우는 **배의 중심선 기준**으로 판정한다. 중앙에 딱 걸리는 애매한 경우도
  가까운 쪽으로 붙여 **왼편/오른편 둘 중 하나**로만 표기한다
  (`S3 중앙` 같은 표기는 두지 않는다)
- "앞/뒤"는 **뱃머리 기준**이다 (S1 = 선수 = 앞)

### 새 데이터가 필요 없다

`ShipyardTwinDashboard.jsx` 의 `mapXYToShipLocalMeters()` 가 배 기준 상대
좌표를 이미 돌려준다:

```js
rel.forward   // 배 앞뒤 방향 거리(m). + 가 뱃머리 쪽
rel.beam      // 배 좌우 방향 거리(m). 부호로 좌/우 판정
```

판정 기준값도 같은 파일에 있다 (`SHIP_REAL_LENGTH_M`, `SHIP_REAL_BEAM_M`,
`SECTION_RANGE`). **순수 계산이고 프론트 파일 하나만 고치면 된다.**

> 사진과 독립적이라 먼저 해도 된다. 로그에 `S3 89%` 만 뜨는 것보다
> `S3 왼편` 이 관제사에게 훨씬 유용하다.

## 2. 스냅샷 — 젯슨이 보내는 것과 백엔드가 할 일

### 젯슨이 보내는 메시지 (완료)

기존 위험 이벤트(fire 등) **직후에 별도 메시지**로 온다.

```json
{
  "event_type": "event_snapshot",
  "block_id":   "B1",
  "event_id":   "fire@0.63,-0.23",
  "cls":        "fire",
  "image_b64":  "/9j/4AAQSkZJRg..."
}
```

- 위험 이벤트 **3종**(`fire` / `fallen_person` / `no_helmet`)에만 온다.
  `level*` 에는 안 온다
- **중복 제거를 통과한 새 이벤트에만** 온다. 같은 자리 불로 계속 오지 않는다
- 이미지는 검출 bbox + 사방 40px 여백을 자른 것. **박스는 안 그려져 있다**
- 보통 10~40 KB
- `event_id` 는 위험 이벤트 메시지의 것과 **정확히 같다.** 이걸로 짝을 짓는다

### 백엔드가 할 일

**① `LOGGED_EVENT_TYPES` 에 `event_snapshot` 을 넣지 말 것**

그대로 저장하면 base64 가 문서에 통째로 들어간다. 그러면
**재접속 복원 때마다 이미지가 전부 다시 흐르고** Atlas 용량도 먹는다.

**② 파일로 저장하고 몽고에는 경로만**

```python
# 파일명: event_id 에 쉼표·@ 가 있어 그대로 쓰면 안 된다
name = hashlib.sha1(event_id.encode()).hexdigest()[:16] + ".jpg"
# backend/snapshots/<hash>.jpg 로 저장

# 새 문서를 만들지 말고, 그 event_id 를 가진 기존 위험 이벤트 문서를 update
{"$set": {"image_url": f"/snapshots/{name}"}}
```

```python
os.makedirs("snapshots", exist_ok=True)          # 폴더가 없으면 mount 가 죽는다
app.mount("/snapshots", StaticFiles(directory="snapshots"), name="snapshots")
```

**③ 프론트로 base64 를 릴레이하지 말 것**

재접속 복원 때 `image_url` 이 붙어 나가므로 그것으로 충분하다.
실시간으로 바로 띄우고 싶으면 **`image_url` 만 담은 가벼운 메시지**로 바꿔 보낸다.

### 왜 몽고에 이미지를 넣지 않는가

| | |
|---|---|
| 용량 | Atlas 무료 512MB. base64 는 원본보다 **33% 커진다** |
| 재접속 복원 | 문서를 통째로 다시 보내므로 **이미지도 전부 다시 흐른다** |
| 브라우저 캐싱 | URL 이면 캐시가 되지만 문서 안 base64 는 매번 새로 받는다 |

**확인은 몽고 창이 아니라 브라우저로 한다:**
`http://192.168.0.5:8000/snapshots/<hash>.jpg`

### 용량 감각

```
crop 1장        20~40 KB
한 세션 이벤트   많아야 20건
                ──────────
세션당           약 600 KB
100 세션         약 60 MB      디스크에는 아무것도 아니다
```

### `.gitignore`

```
backend/snapshots/*          ← 사진 전부 차단
!backend/snapshots/.gitkeep  ← 폴더만 남김
```

**폴더를 남기는 이유** — `backend/snapshots/` 로 통째로 무시하면 새로 clone
했을 때 폴더가 아예 없어서 `StaticFiles(directory="snapshots")` 가 폴더를
못 찾고 서버가 죽는다. 그래서 내용만 막고 폴더는 남긴다.

`os.makedirs(..., exist_ok=True)` 한 줄을 함께 두면 누가 폴더를 지우거나
다른 경로에서 서버를 띄우는 경우까지 막아준다.

> **사진에는 작업자 얼굴이 찍힐 수 있다.** 용량보다 이쪽이 더 중요한 이유다.

### 하지 말 것

- base64 를 이벤트 문서에 그대로 저장 → 재접속 복원 때마다 이미지 폭탄
- 프론트로 base64 릴레이 → 같은 이유
- GridFS → 16MB 넘는 파일용. crop 은 수십 KB라 과하다

## 3. 프론트가 할 일

- 핑·구획 클릭 시 뜨는 팝업에 그 이벤트의 `image_url` 이 있으면
  `<img src={event.image_url}>` 로 한 장 띄운다
- **`image_url` 이 없어도 깨지면 안 된다.** 스냅샷이 아직 안 왔거나
  구버전 이벤트일 수 있다. 그때는 지금처럼 실시간 영상만 보여준다
- 재접속 복원(`replay`)으로 온 이벤트에도 `image_url` 이 실려 오므로
  **같은 코드로 처리된다**

## 4. 젯슨 CPU 부하 — 걱정할 수준이 아니다

중복 제거 덕분에 **이벤트는 드물다.** 프레임마다가 아니라 **새 이벤트당 한 번**.

```
작은 crop JPEG 인코딩   1~5 ms
base64                 1 ms 미만
```

이미 돌고 있는 것과 비교하면 무시할 수준이다:

```
YOLO 추론      매 프레임 (~10 Hz)        ← 가장 무겁다
WebRTC 영상    480×360 5fps 연속 인코딩
뎁스 처리      매 프레임
```

**영상만 해도 초당 5~15장을 계속 인코딩하고 있다.**

> ⚠️ 순서가 중요하다 — **중복 제거를 통과한 뒤에** 인코딩해야 한다.
> 매 프레임 인코딩하고 나서 버리면 초당 수십 번 인코딩하게 되어 얘기가
> 완전히 달라진다. (젯슨 구현은 이 순서를 지키고 있다)

## 5. 사진 최신화 — 보류

원래 아이디어: 로봇이 그 핑 근처를 다시 지날 때 이벤트가 아직 살아있으면,
그때의 사진(신뢰도가 가장 높은 것)으로 갈아끼워 항상 최신 상태를 보여주기.

**지금은 구현하지 않는다.** 모형 화재는 실제 불처럼 커지거나 작아지지 않아
사진을 갱신해도 달라지는 것이 없다.

> **실제 현장에서는 의미가 있다.** 불이 번지거나 잦아드는 것, 쓰러진 사람의
> 상태가 바뀌는 것을 사진으로 추적할 수 있다. 현장 적용 단계에서는 이 기능을
> 추가해 이벤트의 **현황 변화**를 따라갈 수 있도록 한다.
>
> 구현 시 주의: 갱신도 결국 인코딩이므로 **"신뢰도가 기존보다 높을 때만"**
> 같은 조건을 두어 갱신 빈도를 묶어야 한다. 조건 없이 매번 갱신하면
> 4장의 "중복 제거 뒤 인코딩" 원칙이 무너진다.
