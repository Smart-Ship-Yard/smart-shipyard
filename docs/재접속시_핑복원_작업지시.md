# 대시보드 재접속 시 위험 핑 복원 — 작업 지시서

작성: 2026-08-27 (젯슨에서 조사·검증 후 작성)
대상: 백엔드 `backend/main.py`, 프론트 `frontend/src/ShipyardTwinDashboard.jsx`
**젯슨 쪽은 고칠 것 없음** (아래 5번 참고)

---

## 1. 문제

대시보드를 새로고침하거나 재접속하면 **화면에 찍혀 있던 위험 핑이 전부 사라진다.**
불이 실제로 그 자리에 그대로 있어도 핑이 다시 안 뜬다.

원인은 백엔드다. `/ws/frontend` 는 접속을 수락만 하고 아무것도 안 보낸다:

```python
@app.websocket("/ws/frontend")
async def websocket_frontend(websocket: WebSocket):
    await manager.connect(websocket)      # accept 만
    while True:
        raw = await websocket.receive_text()   # 받기만
```

프론트는 WebSocket 으로 들어온 이벤트만 그리므로, 접속 이후에 새 이벤트가
오기 전까지는 빈 화면이다.

**젯슨이 다시 보내주지 않는 이유:** `change_point_detector` 가 이미 보고한
이벤트는 중복 제거로 재발행하지 않는다. 그게 정상 동작이다(같은 자리 불로
로봇이 반복 정지하지 않게 하는 핵심 로직). 그러니 복원은 **서버가 DB 를 보고
해줘야 한다.**

## 2. 백엔드 수정 — 접속 시 살아있는 이벤트 재전송

### 2-1. 헬퍼 추가

`event_collection` 정의(파일 중간, `db = client.shipyard_db` 아래) 이후 아무 데나.

```python
# 위험 이벤트 4종 — 재전송 대상
DANGER_TYPES = {SHIP_DEFECT, NO_HELMET, FALLEN_PERSON, FIRE}


async def _active_danger_events(limit: int = 300):
    """지금도 살아있는 위험 이벤트를 오래된 순으로 돌려준다.

    '살아있다' = 등록(fire 등)된 뒤 같은 event_id 로 event_cleared 가 오지
    않았다는 뜻이다. 젯슨의 change_point_detector 가 "로봇이 그 자리를 다시
    지나갔는데 안 보인다"를 확인해야만 event_cleared 를 보내므로, 이 판정은
    젯슨의 판단을 그대로 따르는 것이다.
    """
    docs = await event_collection.find(
        {"event_type": {"$in": list(DANGER_TYPES) + [EVENT_CLEARED]}}
    ).sort("_id", -1).to_list(length=limit)
    docs.reverse()                      # 오래된 것부터 훑어야 순서가 맞다

    alive = {}
    for d in docs:
        eid = d.get("event_id")
        if not eid:
            continue                    # event_id 없는 구버전 메시지는 건너뛴다
        if d["event_type"] == EVENT_CLEARED:
            alive.pop(eid, None)
        else:
            alive[eid] = d
    return list(alive.values())
```

### 2-2. 접속 직후 재전송

`websocket_frontend` 의 `await manager.connect(websocket)` 바로 다음에 넣는다.
**broadcast 가 아니라 방금 접속한 소켓에만 보낸다** — 이미 보고 있던 다른
대시보드에 핑을 두 번 그리면 안 되기 때문이다.

```python
    await manager.connect(websocket)
    print("🖥️ [프론트엔드] 대시보드 웹소켓 연결됨!")

    # ★ 재접속 복원 (2026-08-27).
    #   프론트는 WebSocket 으로 받은 것만 그리므로 새로고침하면 핑이 전부
    #   사라진다. 젯슨은 중복 제거 때문에 다시 안 보내준다(그게 정상이다).
    #   그래서 서버가 DB 를 보고 살아있는 것만 다시 깔아준다.
    try:
        # 배 위치를 **먼저** 보내야 한다. 프론트가 map_xy -> 구획 좌표를
        # 변환할 때 ship_pose 가 필요한데, 없으면 전부 B1 로 떨어져 핑이
        # 엉뚱한 자리에 찍힌다.
        pose = await event_collection.find_one(
            {"event_type": SHIP_POSE}, sort=[("_id", -1)])
        if pose:
            pose.pop("_id", None)
            await websocket.send_json(pose)

        for doc in await _active_danger_events():
            doc.pop("_id", None)        # ObjectId 는 JSON 으로 못 나간다
            doc["replay"] = True        # ← 프론트가 팝업을 띄우지 않게 하는 표시
            await websocket.send_json(doc)
    except Exception as e:
        # 복원에 실패해도 연결 자체는 살린다. 핑이 안 뜨는 것은 불편이지만,
        # 여기서 예외가 나가면 대시보드가 아예 못 붙는다.
        print(f"⚠️ [프론트엔드] 재접속 복원 실패(무시하고 계속): {e}")
```

### 2-3. 주의

- `replay` 필드는 **DB 에 저장하지 않는다.** 위 코드는 DB 에서 읽어온 dict 에만
  붙이므로 저장 경로와 무관하다.
- `_id` 를 반드시 지울 것. `ObjectId` 는 `send_json` 에서 직렬화 예외가 난다.
- `limit=300` 은 최근 300건만 훑는다는 뜻이다. 그보다 오래된 미해결 이벤트는
  복원 안 된다 — 시연 길이 기준으로 충분하고, 무제한으로 훑으면 접속이 느려진다.

## 3. 프론트 수정 — 복원분은 핑만 그리고 팝업은 띄우지 않는다

**이 수정 없이 백엔드만 고치면 재접속할 때마다 살아있는 이벤트 수만큼 팝업이
연달아 뜬다.** 반드시 같이 해야 한다.

### 3-1. `onMessage` 에서 플래그를 실어 보낸다

`ShipyardTwinDashboard.jsx` 의 `onMessage` → "② 위험 이벤트" 블록.
`handleDetectionEvent({...})` 호출 객체에 한 줄 추가:

```js
        handleDetectionEvent({
          id: `evt_${Date.now()}_${Math.floor(Math.random() * 1e4)}`,
          ts: Date.now(),
          cls: type,
          blockId,
          onShip: conv?.onShip ?? true,
          local: conv?.onShip ? conv.local : { x: 0.5, y: 0.6, z: 0.5 },
          worldX: conv && conv.onShip === false ? conv.worldX : null,
          worldZ: conv && conv.onShip === false ? conv.worldZ : null,
          conf: data.confidence ?? 0,
          eventId: data.event_id ?? null,
          replay: data.replay === true,   // ★ 추가: 재접속 복원분 표시
        });
```

### 3-2. `handleDetectionEvent` 에서 팝업만 건너뛴다

DANGER 분기를 이렇게 바꾼다. **핑(`spawnPing`)과 `dangerByBlockRef` 기록은
그대로 둔다** — 재접속해도 그 블록을 클릭하면 확인 버튼이 떠야 하기 때문이다.

`spawnPing` 은 이 분기 위에서 이미 호출되므로 건드릴 필요 없다.

### 3-3. 로그·통계도 손볼지

함수 끝의 `setEvents` / `setStats` 는 그대로 둬도 되고, 복원분을 빼고 싶으면
`if (!payload.replay)` 로 감싸면 된다. **권장: 그대로 둔다.** 위험 이벤트 로그에
살아있는 항목이 보이는 편이 관제사에게 자연스럽다.

## 4. 검증

1. 백엔드·프론트 띄우고, 젯슨에서 불을 감지시켜 핑 1개를 만든다
2. **팝업 확인을 누른다** (핑은 남아 있어야 한다)
3. 브라우저 새로고침
4. 기대 결과
   - 핑이 **같은 자리에** 다시 뜬다
   - **팝업은 안 뜬다**
   - 그 블록을 클릭하면 확인 버튼이 있는 팝업이 뜬다
5. 젯슨에서 불을 치우고 로봇이 그 자리를 지나가면 → 핑이 사라진다
6. 다시 새로고침 → 핑이 **안 뜬다** (`event_cleared` 가 반영됐다는 뜻)

5·6번이 제일 중요하다. 이게 되면 "치워진 것까지 되살리는" 최악의 버그가 없다는
뜻이다.

## 5. 젯슨 쪽에서 할 일 — 없음

조사해서 확인한 것:

- DB 에 저장된 fire 문서에 프론트가 핑을 그리는 데 필요한 필드가 다 있다:

  ```json
  {"event_type":"fire","confidence":0.916,"map_xy":[0.629,-0.228],
   "event_id":"fire@0.63,-0.23","ekf_global":[-0.225,-0.198],
   "timestamp":"2026-08-27T02:57:28+09:00"}
  ```

  `block_id` 는 없지만 프론트가 `map_xy` + `ship_pose` 로 직접 계산한다
  (`mapXYToPingWorld`). 그래서 **ship_pose 를 먼저 보내는 순서가 중요하다.**

- `ship_pose` 문서도 DB 에 있다 (`block_id`, `map_xy`, `yaw` 포함).

- 젯슨의 `change_point_detector` 는 2026-08-27 부터 이벤트 목록을
  `~/.ros/change_point_events.json` 에 남겨 재시작해도 기억한다. 그래서
  **노드를 재시작해도 같은 자리 불로 로봇이 다시 서지 않는다.** 다만 그건
  젯슨 내부 기억일 뿐이고 프론트에 다시 보내주지는 않는다 — 그래서 이 문서의
  서버 재전송이 필요하다. 두 수정은 서로 독립이고 둘 다 있어야 한다.

## 6. 하지 말 것

- **젯슨이 재발행하게 만들지 말 것.** 중복 제거를 무력화하면 같은 자리 불로
  로봇이 계속 멈춘다. 2026-08-27 에 그 문제로 하루를 썼다.
- **`replay` 를 DB 에 저장하지 말 것.** 저장하면 그 문서가 다음 복원 때도
  `replay:true` 로 나가는 건 무해하지만, 저장 스키마에 임시 표시가 섞인다.
- **broadcast 로 보내지 말 것.** 이미 보고 있던 다른 대시보드에 핑이 중복
  생성된다.
