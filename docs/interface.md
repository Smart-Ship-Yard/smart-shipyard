# 젯슨 → 서버 통신 스펙 (v1.12)

젯슨(UGV)이 백엔드 서버로 보내야 하는 데이터 전부와 그 형식.
연산(추론·좌표 융합·판별)은 전부 젯슨에서 끝내고, 서버는 결과를 중계·저장만 한다.

- **보내는 것** (젯슨 → 서버): ① 위치 핑 · ② 위험 이벤트(②-b 치워짐 · ②-c 감지 사진 포함) · ③ 조립 단계 · ④ 배 위치 — JSON / ⑤ 실시간 영상 — 중앙 미디어 서버로 RTSP push (아래 참조)
- **받는 것** (서버 → 젯슨): ⑧ `event_ack` — 이벤트 확인, 자율주행 재개
- **양방향**: ⑦ `webrtc_signal` — 영상 연결용 시그널링 쪽지 (서버는 그대로 중계)

## 접속 주소

- JSON 채널: `ws://<서버IP>:8000/ws/jetson` — ①~④ 전송 + ⑧ 수신
- (참고) 프론트엔드용: `ws://<서버IP>:8000/ws/frontend`
- **백엔드에 영상 채널은 없다.** 영상은 별개 프로세스인 mediamtx 가 받는다 — `rtsp://192.168.0.5:8554/ugv1` (⑤ 참조)
- 서버 IP는 같은 공유기 내부 IP라 그때그때 공유 (공유기에서 DHCP 고정 할당 예정)

## ① 위치 핑 — DB 저장 안 함

평상시 계속 전송. 주기는 일단 0.5초에 1번으로 시작 (조절 가능).

```json
{"event_type": "position", "ekf_global": [3.2, 7.8]}
```

- `ekf_global` = map 기준 차체 절대좌표 `[x, y]` 미터 — ekf_global(융합) 출력값

## ② 위험 이벤트 — DB 저장 ✅

감지 시에만 전송. conf 0.5 미만은 버림. 같은 상황을 프레임마다 연사하지 말고 안정 감지 시 1번.

```json
{
  "event_type": "fallen_person",
  "confidence": 0.91,
  "map_xy": [1.2, 0.4],
  "event_id": "fallen_person@1.20,0.40",
  "ekf_global": [3.2, 7.8]
}
```

- `event_type` 허용 값 4개: `fallen_person` · `fire` · `no_helmet` · `ship_defect` (모델 클래스 이름 그대로)
- `person`, `helmet` 같은 정상 상태 클래스는 **보내지 않음**
- `confidence` = YOLO conf 그대로 (0.5~1.0)
- `map_xy` = 객체의 map 절대좌표 `[x, y]` 미터. 젯슨이 카메라 좌표를 TF로
  변환하고, **같은 자리(반경 0.5m)의 같은 클래스는 이미 중복 제거한 뒤**
  보낸다 — 로봇이 순찰하며 같은 대상을 여러 번 지나쳐도 한 번만 온다
  (v1.6 이전에는 `depth_xyz`(카메라 상대좌표)를 보냈다. 로봇이 매번 다른
  자리에서 봐서 좌표가 흔들렸고, 재사용도 안 돼 프론트가 직접 map 으로
  환산해야 했다. map_xy 로 바뀌면서 필드도 없앴다)
- `event_id` = 이 위치·클래스에 붙는 안정된 식별자 `"<class>@<x>,<y>"`
  (소수 2자리). 아래 ②-b 치워짐 메시지가 이 값으로 어느 이벤트인지 가리킨다.
  **프론트는 이 값으로 핑을 식별·관리할 것** — 같은 event_id 가 다시 오면
  같은 핑이다(재확인일 뿐, 새 이벤트 아님)
- `ekf_global` = 감지한 순간의 차체 위치
- `timestamp`는 서버가 자동으로 붙임 → **보내지 마**

## ②-b 위험 이벤트 치워짐 — DB 저장 ✅ (v1.6 신설)

로봇이 이미 보고한 이벤트의 자리를 다시 지나가며 지켜봤는데(3초 이상)
더 이상 안 잡히면 보낸다. **프론트는 이 메시지를 받으면 해당 event_id 의
빨간 핑을 지울 것.**

```json
{
  "event_type": "event_cleared",
  "block_id": "B1",
  "cls": "fire",
  "map_xy": [0.40, -0.99],
  "event_id": "fire@0.40,-0.99"
}
```

- `cls` = 치워진 이벤트의 클래스 (② 의 `event_type` 허용 값 4개 중 하나).
  이 메시지 자체의 `event_type` 은 `"event_cleared"` 고정이라 클래스를
  따로 실어야 해서 별도 키를 쓴다
- `map_xy`, `event_id` = ② 에서 처음 그 이벤트를 보고할 때 쓴 것과 동일한 값
- 예: 화재 진화 후 로봇이 그 옆을 다시 지날 때, 사람이 헬멧을 쓰고 로봇이
  다시 지날 때, 쓰러졌던 사람이 일어나서 로봇이 다시 지날 때

### ★ 이 메시지는 대시보드 복원의 유일한 판정 근거다

서버는 대시보드가 접속할 때 **아직 살아있는 위험 이벤트**를 다시 보내준다
(새로고침해도 핑이 남게 하기 위함). 이때 "살아있다"의 판정은
**같은 `event_id` 로 `event_cleared` 가 왔는지 하나뿐이다.**

즉 `event_cleared` 를 안 보내면 그 이벤트는 **영원히 살아있는 것으로 남아**
새로고침할 때마다 계속 복원된다. `event_id` 는 등록 때와 **글자 단위로 같아야**
짝이 맞는다.

> 서버는 그 대신 **자기가 켜진 시각 이후**의 이벤트만 복원한다. 재시작이
> 이전 세션의 찌꺼기를 끊어주는 유일한 장치다 (`backend/README.md` 참고).

## ②-b-2 재연결 시 생존 재통보 (`replay: true`) — DB 저장 ❌ (v1.11 신설)

젯슨이 서버에 **(재)연결할 때**, 지금 살아있는 위험 이벤트를 다시 보낸다.
② 와 형식이 같고 `"replay": true` 가 하나 붙는다.

```json
{
  "event_type": "fire", "confidence": 0.92,
  "map_xy": [-0.40, -1.38], "event_id": "fire@-0.40,-1.38",
  "ekf_global": [...],
  "replay": true
}
```

**왜 필요한가** — 서버가 재시작하면 대시보드는 빈 화면으로 시작한다. 그런데
로봇의 `change_point_detector` 는 그 불을 이미 기억하고 있어 재발행하지 않는다.
`event_ttl` 도 소용없다 — 로봇이 순찰하며 계속 그 불을 보면 `last_seen` 이
갱신돼 만료되지 않는다. **불이 눈앞에 있는데 화면은 무기한 비어 있게 된다.**

### 서버가 하는 일

- **DB 에 저장하지 않는다.** 이미 있는 이벤트의 중복 기록이고, 실제로 그 시각에
  감지된 것도 아니라 감사 기록을 흐린다
- 대신 그 `event_id` 를 **생존 목록**에 넣는다. 복원할 때 서버 시작 시각 아래의
  기록이어도 이 목록에 있으면 함께 꺼내온다 — 저장하지 않으면서도 새로고침에
  살아남게 하기 위함이다
- **처음 보는 event_id 면 저장한다.** 서버가 꺼져 있는 동안 처음 감지된 불은
  이 재통보가 **유일한 전달 경로**다. 안 남기면 DB 에 기록이 아예 없어, 생존
  목록에 id 는 있는데 꺼내올 문서가 없다 — 핑이 떴다가 새로고침하면 사라진다.
  저장할 때 `replay` 플래그를 지우지 않는다: 나중에 감사할 때 그 timestamp 를
  감지 시각으로 오해하지 않기 위함이다
- `event_cleared` 가 오면 목록에서 뺀다
- 젯슨 연결이 새로 열리면 목록을 비우고 그 연결의 재통보로 다시 채운다

**젯슨이 이 판정의 주인이다.** 로봇이 그 자리를 다시 보고 확인하므로, 며칠 전
DB 기록보다 훨씬 믿을 만하다.

프론트는 ② 와 똑같이 처리하되 `replay` 가 붙은 것은 **팝업을 띄우지 않는다**
(새로고침·재연결마다 팝업이 연달아 뜨는 것을 막기 위함). 핑과 구획 강조는 그린다.

## ②-c 감지 순간 사진 — DB에 통째로 저장 ❌ / 파일로 저장 ✅ (v1.8 신설)

위험 이벤트를 보낸 **직후 별도 메시지**로, 그 순간의 잘라낸 사진을 보낸다.
대시보드에서 핑이나 구획을 눌렀을 때 "그때 무슨 일이 있었나"를 보여주기 위함이다.

```json
{
  "event_type": "event_snapshot",
  "block_id":   "B1",
  "event_id":   "fire@0.63,-0.23",
  "cls":        "fire",
  "image_b64":  "/9j/4AAQSkZJRg..."
}
```

- **위험 3종에만** 온다 — `fire` · `fallen_person` · `no_helmet`.
  `block_level` 같은 데는 안 온다
- **중복 제거를 통과한 새 이벤트에만** 온다. 같은 자리 불로 계속 오지 않는다
- `event_id` 는 ② 에서 그 이벤트를 보고할 때 쓴 것과 **글자 단위로 같다.**
  서버는 이 값으로 짝을 지어 기존 이벤트 문서에 사진을 붙인다
- `image_b64` = 검출 박스 + 사방 40px 여백을 자른 JPEG 을 base64 로 인코딩한 것.
  **박스는 그려져 있지 않다.** 보통 10~40 KB
- `cls` = ②-b 와 같은 이유로 클래스를 따로 실어 보낸다

### ★ 서버는 base64 를 저장하지도, 흘려보내지도 않는다

받자마자 **파일로 떨어뜨리고 주소만 남긴다.**

```
젯슨 ──image_b64──▶ 서버 ──파일──▶ backend/snapshots/<event_id 해시>.jpg
                     │
                     ├─ 몽고: 그 event_id 의 위험 이벤트 문서에 image_url 만 추가
                     └─ 프론트: {"event_type":"event_snapshot", ..., "image_url":"/snapshots/....jpg"}
```

프론트가 받는 메시지에는 `image_b64` 가 **없고** `image_url` 만 있다.
`http://<서버주소>/snapshots/<해시>.jpg` 로 바로 열린다.

이렇게 하는 이유는 대시보드 복원 때문이다. 복원은 이벤트 문서를 그대로 다시
보내는 구조라, base64 를 문서에 넣으면 **새로고침할 때마다 살아있는 이벤트의
사진이 전부 다시 흐른다.** URL 이면 브라우저가 캐시해 두 번째부터는 안 받는다.
(base64 는 원본 바이트보다 33% 크기까지 하다.)

> ⚠️ 사진에는 작업자 얼굴이 찍힐 수 있다. `backend/snapshots/` 는
> `.gitignore` 로 커밋이 막혀 있다 — 절대 풀지 말 것.

**확인은 몽고 창이 아니라 브라우저로 한다** — 몽고에는 주소밖에 없다.

## ③ 조립 단계 변화 — DB 저장 ✅

단계가 바뀌었을 때 1번 + 부팅·재접속 시 현재 단계 1번.

```json
{"event_type": "block_level", "block_id": "B1", "level": 2}
```

- `level` = 클래스 이름(level1/2/3)이 아니라 **숫자만** 1, 2, 3
- `block_id` = 당분간 `"B1"` 고정 (배 1척이라)
- YOLO가 프레임마다 흔들리니, 몇 초간 같은 단계로 안정 감지됐을 때만 "바뀜"으로 인정

## ④ 배 위치 (측량 결과) — DB 저장 ✅

세션 시작 측량 후 1번 + **조립 단계가 바뀔 때마다** 재측량 후 1번 (직접 조립하는 과정에서 배가 밀리거나 돌아갈 수 있음).

```json
{"event_type": "ship_pose", "block_id": "B1", "map_xy": [5.1, 4.8], "yaw": 1.57}
```

- `map_xy` = 배 중심의 map 좌표 `[x, y]`, 미터
- `yaw` = **뱃머리가 향하는 방향**, 라디안 (map `+x` 기준 반시계).
  `yaw=0` 이면 뱃머리가 map `+x` 축을 향한다.
- 실시간 아님 — 측량이 끝났을 때만 1번씩
- 서버가 저장해뒀다가 프론트 초기 로딩(init-data)에 제공 → 3D 배 모델 배치에 쓰임

### ★ 운영 규칙: 배는 항상 map `+x` 방향으로 뱃머리가 가게 놓는다

`map +x` 는 **UWB 캘리브레이션 때 로봇이 직진한 방향**이며, 바닥에 시작점·끝점
테이프로 표시돼 있다. 그 테이프가 가리키는 방향에 뱃머리를 맞추면 된다.

**왜 이 규칙이 필요한가** — 측량은 배를 **직사각형** 하나로 인식한다
(`cv2.minAreaRect`). 직사각형은 180도 돌려도 똑같이 생겨서 **어느 쪽이 뱃머리인지
기하학적으로 구분할 수 없다.** 항상 같은 방향으로 놓기로 약속하면 그 모호성이
사라진다. 젯슨의 `ship_survey_node` 는 이 규칙을 전제로 `yaw_hint_rad=0.0`
기본값을 쓴다.

| 쪽 | 이 규칙이 깨지면 |
|---|---|
| 프론트 | 3D 배 모델이 180도 뒤집혀 보인다 |
| Nav2 | **영향 없음.** keepout 마스크는 축정렬 사각형이고 직사각형은 180도 대칭이라 금지 영역이 같다. 순찰 원도 회전 대칭이다 |
| 백엔드 | 영향 없음. 값을 변환하지 않고 그대로 중계·저장한다 |

프론트는 3D 모델의 forward 축이 `yaw=0` 에서 map `+x` 를 향하도록 맞춘다.

## ⑤ 실시간 영상 — 중앙 미디어 서버를 거친다

영상은 **백엔드 애플리케이션을 거치지 않지만, 중앙 미디어 서버는 거친다.**
젯슨이 H.264 로 한 번만 인코딩해 서버의 mediamtx 로 밀어올리고(RTSP push),
브라우저는 그 mediamtx 에 WebRTC 로 붙는다.

```
젯슨 ──H.264 스트림 1개, RTSP push──▶ mediamtx(중앙) ──WebRTC──▶ 브라우저 N명
```

- 화질 기준: 평상시 480×360/5fps 수준 — WebRTC 가 회선 상태를 보고 알아서 조절한다
- 접속 주소: `http://192.168.0.5:8889/ugv1` (mediamtx 의 WebRTC 재생 페이지)
- 젯슨 송출 주소: `rtsp://192.168.0.5:8554/ugv1` (ffmpeg 이 `-rtsp_transport tcp` 로 민다)
- 서버 노트북은 공유기에서 **고정 IP 192.168.0.5** 로 잡아두어 바뀌지 않는다

### ★ P2P 가 아니다

WebRTC 를 쓰지만 양쪽이 대등한 P2P 는 아니다. mediamtx 가 미디어 서버이고
브라우저가 거기 접속하는 client-server 구조다.

### ★ 왜 미디어 서버를 거치나 — 애플리케이션 서버가 아니라 미디어 서버다

백엔드(FastAPI)로 영상을 나르려면 JPEG(MJPEG) 프레임을 웹소켓으로 밀어야
한다. 그러면 프레임 간 압축과 혼잡 제어를 잃는다:

| | 백엔드 중계 (MJPEG) | 미디어 서버 (H.264/WebRTC) |
|---|---|---|
| 대역폭 | 3~5배 | 기준 |
| 혼잡 제어 | 없음 — 밀리면 프레임이 쌓여 지연이 눈덩이 | WebRTC 가 스스로 화질을 낮춰 버틴다 |
| 젯슨 인코딩 | 프레임마다 JPEG 재인코딩 | H.264 한 번 |
| 표준성 | 우리만 쓰는 방식 | 상용 관제 시스템(VMS)에 그대로 물림 |

**거치는 게 나쁜 게 아니라 MJPEG 로 거치는 게 나쁘다.** 그래서 H.264 를
유지한 채 미디어 서버를 거친다.

> **백엔드에는 영상 폴백 경로가 없다.** 예전에 있던
> `/ws/jetson-stream → /ws/frontend-stream` 은 **2026-08-28 코드에서 삭제했다.**
> 젯슨이 그 창구로 프레임을 보낸 적이 한 번도 없어서 "폴백"이라 적혀 있었을 뿐
> 실제로는 동작하지 않았다 — 시연 중에 전환했다면 검은 화면만 나왔을 것이다.
> 영상이 안 나오면 폴백을 찾지 말고 mediamtx 와 방화벽을 본다.

### ★ 왜 인코딩을 한 번만 하나 — 제약은 CPU 였다

젯슨 6코어에서 **Nav2 자율주행 · YOLO 추론 · 영상 송출을 동시에** 돌려야 했다.
CPU 가 포화되면 Nav2 의 lifecycle 전환이 타임아웃되고, 그러면 자율주행이
통째로 실패한다. **실제로 겪었다(2026-08-18).**

실측 (2026-08-27, 이전 전):

```
ffmpeg     42.2% of 1 core   H.264 인코딩
mediamtx    1.2% of 1 core
────────────────────────────
합계       0.43 코어
```

중앙으로 옮기면 mediamtx 몫이 서버로 넘어가 젯슨은 **0.42 코어**가 된다.
수치보다 중요한 것은 **시청자 수에 비례하지 않게 된다**는 점이다 — 젯슨은
몇 명이 보든 스트림 하나만 올려보낸다.

이전 후 실측으로 확인했다 (2026-08-28): 시청자를 1명에서 3명으로 늘려도
젯슨의 ffmpeg CPU 는 44.0% → 44.2%, RTSP 세션은 **1개 그대로**였다.
브라우저는 젯슨의 8889 에 아예 붙지 않는다.

### 이전 전후 비교

```
[이전]  젯슨(mediamtx) ──WebRTC──▶ 브라우저        시청자 수만큼 젯슨이 부담
                                                  다른 망에서는 접속 불가
[현재]  젯슨 ──H.264 1개──▶ mediamtx(중앙) ──▶ 브라우저 N명
```

젯슨 쪽은 **코드를 고치지 않았다.** systemd 환경변수 한 줄이다:

```
Environment=RTSP_URL=rtsp://192.168.0.5:8554/ugv1
```

서버 쪽 설치·방화벽·검증 절차는
[`server/streaming/README.md`](../server/streaming/README.md) 에 있다.

### ⚠️ 방화벽 — 8189/udp 를 빠뜨리지 말 것

서버에서 세 포트를 열어야 한다. **UDP 하나가 섞여 있다.**

| 포트 | 방향 | 쓰임 |
|---|---|---|
| 8554/tcp | 젯슨 → 서버 | RTSP push |
| 8889/tcp | 브라우저 → 서버 | WebRTC 시그널링 + 재생 페이지 |
| **8189/udp** | 브라우저 ↔ 서버 | **WebRTC ICE 미디어** |

8889 만 열면 재생 페이지는 뜨는데 **영상이 영원히 안 나온다.** 시그널링은
8889 로 하지만 실제 영상은 ICE 로 뚫은 UDP 로 흐르기 때문이다. 에러도 없이
검은 화면이라 원인을 찾기 어렵다.

### ⚠️ 인증 — 아직 열려 있다

mediamtx 는 `authMethod: http` 로 **외부 HTTP 엔드포인트에 인증을 위임**할 수
있다. 백엔드에 로그인이 생기면 그쪽에 물어보게 묶는다. 지금은 백엔드에
인증 자체가 없어 열어둔 상태이며, **같은 망의 누구나 볼 수 있다.**
현장 적용 전 반드시 막을 것.

백엔드 인증 없이 mediamtx 에만 비밀번호를 거는 것은 의미가 없다 —
프론트 소스에 그 비밀번호가 박히기 때문이다.

### 녹화 (미구현)

mediamtx 가 녹화를 지원한다. 켤 때 알아둘 것:

- 용량: 실측 **1.2 Mbps** 기준 **시간당 약 540 MB, 하루 약 13 GB**.
  (2026-08-28 이전 직후 젯슨→서버 전송량 152 KB/s 측정. 그 전 추정치는
  1.5 Mbps 였는데 실제로는 그보다 낮았다.)
  `recordDeleteAfter` 로 보관 기간을 반드시 걸 것.
- **몽고에 새 필드를 넣지 않는다.** 사진은 이벤트 1건 = 파일 1개라 URL 을
  저장하지만, 녹화는 시간축으로 이어지므로 이벤트의 `timestamp` 로 조회한다:

```
http://192.168.0.5:9996/get?path=ugv1&start=<timestamp>&duration=15
```

  (조회 API 는 `playback: true` 를 켜야 열린다 — 지금은 꺼져 있다)

## ⑦ webrtc_signal — 시그널링 쪽지 (양방향, DB 저장 안 함)

WebRTC 연결 성사 전에 젯슨↔프론트가 교환해야 하는 연결 정보(SDP offer/answer, ICE candidate).
**payload 내용은 WebRTC 라이브러리(브라우저 API / aiortc 등)가 자동 생성** — 사람이 정하거나 읽을 필요 없음.
서버는 내용을 열어보지 않고 반대편으로 그대로 배달한다.

```json
{"event_type": "webrtc_signal", "payload": { ...라이브러리가 만든 SDP/ICE 그대로... }}
```

- 프론트가 `/ws/frontend`로 보내면 → 서버가 젯슨(`/ws/jetson`)으로 전달
- 젯슨이 `/ws/jetson`으로 보내면 → 서버가 프론트로 브로드캐스트
- 규칙은 하나: **양쪽 다 이 봉투(event_type + payload)에 담아 보낼 것**

## ⑧ event_ack — 이벤트 확인 (프론트 → 서버 → 젯슨), DB 저장 안 함

관제자가 위험 이벤트 팝업의 **"확인" 버튼**을 눌렀을 때 프론트가 보낸다.
젯슨의 Nav2가 이 신호를 받으면 **정지해 있던 자율주행을 재개**한다.

```json
{"event_type": "event_ack"}
```

### ★ "해결"이 아니라 "확인"이다

실제 화재는 진화에 오래 걸리는데 그동안 로봇이 그 자리에 묶여 있으면
**다른 위험 상황을 즉각 발견할 수 없다.** 관제자가 "봤다"고 알려주면
로봇은 순찰을 계속한다. **프론트 버튼 라벨도 "처리 완료"가 아니라 "확인"** 으로 한다.

- 프론트는 **기존 `/ws/frontend` 소켓**을 그대로 쓴다. 새 연결·새 API 불필요
- 서버는 내용을 판단하지 않고 젯슨으로 그대로 배달 (`webrtc_signal`과 같은 경로)
- 프론트가 부가 필드(어떤 이벤트를 확인했는지 등)를 넣어도 젯슨까지 그대로 전달됨
- 응답 없음 — 보내고 팝업을 닫으면 된다

**젯슨 쪽 처리:** `websocket_client.py`가 수신한 메시지를 해석하지 않고
`/server/inbound` (`std_msgs/String`) 토픽으로 그대로 발행하면,
Nav2 쪽 노드가 `event_ack`를 걸러내 순찰을 재개한다.
서버→젯슨 메시지가 늘어나도 이 통로 하나로 처리된다.

## ⑨ jetson_status — 로봇 연결 상태 (서버 → 프론트), DB 저장 안 함

젯슨이 만드는 메시지가 아니다. **서버가 스스로 판단해서 프론트에 알린다.**

```json
{"event_type": "jetson_status", "connected": false}
```

보내는 시점은 셋이다:

- 젯슨이 `/ws/jetson` 에 연결됐을 때 → `connected: true`
- 젯슨 연결이 끊겼을 때 → `connected: false`
  (재접속으로 옛 연결만 정리되는 경우는 보내지 않는다 — 새 연결이 이미 알렸다)
- **대시보드가 새로 접속했을 때** → 그 순간의 상태

### ★ 왜 필요한가

로봇이 꺼져도 **화면의 위험 핑은 그대로 남는다.** 위험이 사라진 게 아니므로
맞는 동작이다. 문제는 화면이 평소와 똑같아 보인다는 것이다 — 실시간 순찰
정보만 조용히 멈추고, 관제사는 그 사실을 모른다.

프론트는 이 메시지로 팝업을 띄운다:

| 상태 | 문구 |
|---|---|
| `false` | "로봇과의 연결이 끊겼습니다. 로봇과 재연결될 때까지 실시간 순찰 정보 관제가 제한됩니다." |
| `true` | "로봇과 재연결되었습니다. 실시간 순찰 정보 관제를 재개합니다." |

**상태가 바뀔 때만** 띄운다. 다만 대시보드를 여는 순간 이미 끊겨 있으면 그것도
알려야 하므로, 첫 수신이어도 `false` 면 띄운다. 첫 수신이 `true` 면 평상시라
조용히 넘어간다.

확인 버튼을 안 눌러 팝업이 떠 있는 채로 상태가 또 바뀌면, **최신 상태가 이긴다** —
옛 팝업이 자동으로 닫히고 새 팝업으로 바뀐다.

## JSON 키 전체 요약

| 키 | 타입 / 허용 값 | 들어가는 메시지 |
|---|---|---|
| `event_type` | 문자열 — 전송: position · fallen_person · fire · no_helmet · ship_defect · event_cleared · event_snapshot · block_level · ship_pose / 수신: event_ack / 양방향: webrtc_signal | 모든 메시지 (필수) |
| `ekf_global` | 숫자 2개 배열 [x, y], 미터 | ① 위치 핑, ② 위험 이벤트 |
| `confidence` | 숫자 0.5~1.0 | ② 위험 이벤트 |
| `event_id` | 문자열 `"<class>@<x>,<y>"` | ② 위험 이벤트, ②-b 치워짐, ②-c 감지 사진 |
| `cls` | 문자열 — ② 의 event_type 허용 값 4개 중 하나 | ②-b 치워짐, ②-c 감지 사진 |
| `block_id` | 문자열, `"B1"` 고정 | ②-c 감지 사진, ③ 조립 단계, ④ 배 위치 |
| `level` | 정수 1 · 2 · 3 | ③ 조립 단계 |
| `map_xy` | 숫자 2개 배열 [x, y], 미터 — ② 는 객체 위치, ②-b 는 치워진 자리, ④ 는 배 중심 | ② 위험 이벤트, ②-b 치워짐, ④ 배 위치 |
| `yaw` | 숫자, 라디안 — **뱃머리 방향** (map +x 기준 반시계) | ④ 배 위치 |
| `image_b64` | 문자열 — crop JPEG 의 base64 (보통 10~40KB) | ②-c 감지 사진 (젯슨 → 서버 **한 구간만**) |
| `image_url` | 문자열 `"/snapshots/<해시>.jpg"` — **서버가 만든다** | ②-c 감지 사진 (서버 → 프론트), 복원되는 ② 위험 이벤트 |
| `connected` | true · false | ⑨ jetson_status (서버 → 프론트) |
| `replay` | true — 재통보임을 표시 | ②-b-2 생존 재통보 (젯슨 → 서버 → 프론트) |
| `payload` | WebRTC 라이브러리가 생성한 SDP/ICE 객체 그대로 | ⑦ webrtc_signal |
| `timestamp` | 서버가 자동 추가 — 젯슨은 생략 | DB 저장 대상 6종 |

## 공통 규칙

- **철자 정확히.** 서버는 모르는 event_type을 에러 없이 조용히 무시함 — 오타 나면 아무 일도 안 일어나서 디버깅 지옥임. 위 표에서 복붙 권장.
- **실시간 영상**은 이벤트 JSON에 넣지 않음 — WebRTC 채널이 항상 흐르니까 프론트가 거기서 봄.
  단 **감지 순간 사진 한 장**은 예외로 ②-c 로 보낸다 (영상은 지금을 보여주고, 사진은 그때를 보여준다).
  그 경우에도 base64 가 흐르는 구간은 **젯슨 → 서버 한 구간뿐이다.**
- JSON은 텍스트 프레임, 영상은 바이너리 프레임 — 채널을 섞지 말 것.

## 좌표계 메모

- `ekf_global`의 원점·축 정의(맵 만드는 방식)는 슬램 쪽에서 확정한 그대로 가되, 프론트(3D 매핑)와 **직접** 공유 필요. 서버는 좌표를 변환하지 않고 그대로 중계·저장만 함.
- 배(블록) 위치는 ④ `ship_pose` 메시지로 정식 편입됨 — 세션 시작 + 조립 단계 변경 시마다 재측량해서 전송. 프론트는 이 값으로 3D 배 모델을 배치하므로, 이게 틀어지면 로봇 마커가 배를 뚫고 다니는 화면이 됨.
