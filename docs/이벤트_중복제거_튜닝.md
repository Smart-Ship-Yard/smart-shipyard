# 이벤트 중복 제거 · 치워짐 확인 튜닝 가이드

`change_point_detector`(`edge/ros2_ws/src/ship_ugv_perception/ship_ugv_perception/change_point.py`)의
파라미터를 언제 어떻게 바꿔야 하는지 적어둔다. **순찰 반지름이나 카메라 배치를 바꿀 때 이 문서를 볼 것.**

작성: 2026-08-24 (실물 테스트 중 사고 8건을 겪고 정리)
갱신: 2026-08-27 (사고 3건 추가 · 시나리오 1~5 전부 통과 · dedup_radius 0.5 -> 0.35)

---

## 1. 요구사항 (이게 기준이다)

| # | 동작 |
|---|---|
| ① | 불을 처음 인식하면 정지 + 프론트 팝업 + 핑 |
| ② | 확인 후 재개, **같은 자리에 그대로 있으면 다시는 정지하지 않는다** |
| ③ | 배에 가려 안 보이는 구간이 있어도 **핑은 계속 유지된다** |
| ④ | **불이 자리를 옮겼을 때만** 다시 정지한다 |
| ⑤ | 옮기면 이전 자리 핑은 지우고, 새 자리에 새 핑을 찍는다 |

---

## 2. 3단 구조

```
yolo_depth_publisher          검출 (u, v, depth) — 화면좌표
        │  /event_detection/uvd
        ▼
change_point_detector         map 좌표 변환 + 중복 제거 + 치워짐 확인
        │  /event_detection/map_point      (새 이벤트만)
        │  /event_detection/cleared        (치워짐 확인)
        ▼
event_gate_node (정지)  ·  websocket_client (서버 전송)
```

**중요:** `event_gate_node` 와 `websocket_client` 는 원본 `/uvd` 를 보지 않는다.
반드시 `change_point_detector` 의 출력만 본다. 이게 안 지켜지면 중복 제거가
통째로 무력화된다 (2026-08-21 사고, 커밋 d025420).

## 3. 파라미터

| 파라미터 | 현재값 | 역할 |
|---|---|---|
| `dedup_radius_m` | **0.35 m** | 이 반경 안이면 "같은 이벤트" — 재발행 안 함 (② ④를 가름) |
| `event_ttl_s` | 600 s | 이만큼 재검출 없으면 목록에서 잊는다 |
| `revisit_radius_m` | 0.35 m | 처음 불을 본 **로봇 위치**에 이만큼 가까우면 "돌아왔다" |
| `revisit_yaw_tol_deg` | 45° | 헤딩도 비슷해야 카메라가 같은 곳을 본다 |
| `revisit_grace_s` | 3 s | 그 자리에서 이만큼 안 보이면 "치워졌다" (③ ⑤를 가름) |
| `max_depth_m` | 2.0 m | 이보다 먼 검출은 버린다 (유령 이벤트 차단) |
| `min_confidence` | 0.5 | 이 미만 검출은 무시 |

이 노드는 **파라미터 변경 콜백이 없다.** `ros2 param set` 은 안 먹힌다.
값을 바꾸려면 코드를 고치고 `colcon build` 후 노드를 재시작해야 한다.

## 4. ★ 치워짐 판정은 "처음 본 자리로 돌아왔는가"로 한다

### 문제 — 가림과 없어짐을 시간으로는 못 가른다

순찰 원의 **중심에 배가 있다.** 로봇이 배 반대편으로 돌면 배가 불을 가려 검출이
끊긴다. `in_camera_fov()` 는 "카메라가 그 방향을 향하는가"만 각도로 볼 뿐
**가림(occlusion)은 모른다.** 그래서 각도상 FOV 안이라 게이트를 통과하고,
검출이 없으니 "치워졌다"고 오판한다.

실측 (2026-08-24 20:53, 반지름 1.00 m):

```
20:53:20 ~ 20:53:40   fire 59건 검출 (최대 공백 1.00초)  ← 잘 보임
20:53:40              검출 끊김 — 배 뒤로 들어감
20:54:10              검출 재개
  => 가림 구간 약 30초, 한 바퀴 약 50초
```

처음에는 "마지막으로 본 지 N초" 로 풀려 했다. 가림(30초)을 오판하지 않으려면
N 이 그보다 커야 해서 60초가 됐고, 그 대가로 **최악 2.2바퀴(약 110초)** 가
걸렸다. N 을 줄이면 한 바퀴마다 오판이 나 재등록·재정지가 반복됐다.

### 해법 — 로봇 자신의 위치를 신호로 쓴다

그 불을 **처음 검출한 순간의 로봇 위치**에서는 불이 분명히 보였다(그래서
검출됐다). 그러니 그 자리로 다시 왔는데 안 보이면, 가려진 게 아니라 진짜
없는 것이다. **가림 여부를 추측할 필요가 사라진다.**

이벤트를 만들 때 `seen_from`(로봇 위치)과 `seen_yaw`(그때 헤딩)를 함께 저장하고,
`_check_clear` 는 이렇게 판정한다:

```
로봇이 seen_from 에서 revisit_radius_m 밖  -> 대기 (left_vantage 켜둠)
헤딩이 seen_yaw 와 revisit_yaw_tol_deg 밖  -> 대기 (다른 데를 보고 있다)
아직 그 자리를 벗어난 적 없음              -> 대기 (첫 검출 직후다)
revisit_grace_s 안에 본 적 있음            -> 대기 (아직 있다)
그 외                                      -> 치워짐 확정
```

`left_vantage` 가 필요한 이유: 막 검출해 아직 그 자리에 있는 동안 YOLO 가 몇
프레임 놓친 것만으로 지우면 안 된다(프론트 핑이 반짝하고 꺼지던 사고). 예전의
`has_left_once` 는 기준이 `clear_radius_m`(2.0 m)라 순찰 기하상 **영영 못
벗어나** clear 가 아예 발동하지 못했지만, 여기서는 기준이 `revisit_radius_m`
(0.35 m)이라 한 바퀴만 돌면 반드시 벗어난다.

### 결과

| | 예전 (시간 기준) | 지금 (위치 기준) |
|---|---|---|
| 치워짐 확인까지 | 60~110초 (최대 2.2바퀴) | **한 바퀴 안** |
| 순찰 반지름 바꾸면 | `clear_watch_s` 재계산 필요 | **그대로 둬도 됨** |
| 가림 오판 | 시간 여유로 회피 | 구조적으로 불가능 |

**순찰 반지름을 바꿔도 이 값들은 안 건드려도 된다.** 로봇이 어떤 궤도를 돌든
"처음 본 자리로 돌아온다"는 조건은 그대로 성립하기 때문이다.

### 튜닝

- `revisit_radius_m` (0.35): 너무 작으면 그 자리를 정확히 못 밟아 판정이 밀린다.
  너무 크면 아직 멀리서 "돌아왔다"고 판정해 오판이 는다. 순찰 웨이포인트 간격
  (반지름 1.00 · 12개 기준 약 0.52 m)의 절반쯤이 적당하다.
- `revisit_grace_s` (3.0): 그 자리를 지나가는 몇 초 동안 YOLO 가 잡을 기회를
  준다. 검출 주기가 4 Hz 이므로 3초면 10프레임 이상이다.
- `revisit_yaw_tol_deg` (45): Nav2 복구 회전 중에 우연히 그 자리를 밟았을 때
  엉뚱한 방향을 보며 판정하는 것을 막는다.

## 5. `dedup_radius_m` — 하나의 반경이 두 요구를 겸임한다

이 값 하나가 상충하는 두 요구를 동시에 만족시켜야 한다:

- **크게** → "각도 바뀌어도 같은 불로 봐라" (② 유리)
- **작게** → "옮기면 다른 불로 봐라" (④ 유리)

### 변천사 (전부 실측 근거)

| 값 | 결과 |
|---|---|
| 0.5 | 초기값 |
| 1.0 (커밋 8428374) | **오진이었다.** "각도 바뀌면 재등록" 을 고치려 키웠는데, 실제 원인은 clear 오판이 목록에서 먼저 지운 것이었다 (재등록 좌표가 14cm 차이라 0.5로도 매칭됐을 거리) |
| 0.0 (커밋 d81c9b7) | 데모 당일 임시 비활성화 |
| 0.5 | 근본 원인(clear 오판)이 해결돼 되돌림 |
| **0.35 (현재)** | 실측 안전구간의 가운데로. 아래 "안전구간" 참고 |

**1.0 이 낸 실제 피해:** 불을 0.9 m 옮겼는데 1.0 m 반경 안이라 "같은 불"로
매칭돼 정지도 팝업도 안 떴다. **테스트할 때 `dedup_radius_m` 보다 확실히 멀리
옮길 것** (0.5 이면 최소 0.7 m 이상 권장).

### ★ 안전구간 — 이 값을 바꾸려면 여기부터 읽을 것

`dedup_radius_m` 은 감으로 정하는 값이 아니다. 실측 두 가지가 상한과 하한을
동시에 정한다.

**하한** — 제자리 흔들림보다 커야 한다. 같은 불을 110초간 12번 재보니:

```
흩어짐 중앙값 0.04 m / 최대 0.10 m
  로봇(-0.57,-0.22) yaw   -9.8° -> 불(-0.27,-1.20)
  로봇(+0.48,-2.00) yaw -160.6° -> 불(-0.32,-1.19)    ← 순찰 원 정반대편
  로봇(-0.65,-1.69) yaw +129.4° -> 불(-0.24,-1.18)
```

**시점 편향은 사실상 없다.** 어디서 보든 4 cm 안쪽이다. 그러므로 하한은
0.10 m 남짓.

**상한** — 잡아내고 싶은 최소 이동보다 작아야 한다. 이동거리 측정 오차는
실측 -0.06 ~ +0.11 m 이므로, 0.7 m 이동이 최악 0.59 m 로 읽힌다. 그러므로
상한은 0.59 m.

```
안전구간  0.15 ~ 0.55 m
   0.5  → 흔들림 여유 0.40 m / 이동감지 여유 0.09 m   (한쪽으로 쏠림)
   0.35 → 흔들림 여유 0.25 m / 이동감지 여유 0.24 m   (균형)
```

**반경을 줄이면 오탐이 는다는 직관은 여기서 틀린다.** `new_event_confirm_frames`
가 "오측정 둘이 이 반경 안에서 서로 일치할 것"을 요구하므로, 반경이 작을수록
새 이벤트 확인이 **더 엄격해진다.**

#### 0.35 로 전환 후 실물 재검증 (2026-08-27 저녁, 1~5번 전부 통과)

| 확인 | 결과 |
|---|---|
| 3바퀴 재정지 | **0회** (fire 22건 검출하면서도 재발행 없음) |
| 치워짐 | **39초** (한 바퀴) |
| 0.5 m 이동 감지 | 자 50 cm → 계산 **0.47 m** → 새 이벤트 + 정지 |
| 옛 핑 삭제 | 새 등록 95초 뒤 자동 정리 |

**0.47 m 는 0.5 였다면 놓쳤을 거리다.** 이것이 0.35 로 내린 실익이다.
옛 이벤트가 살아있는 상태에서 옮겼으므로(중간에 치워짐 없음) 반경이 실제로
판정에 쓰인 시험이다 — 치워짐이 먼저 나가면 목록이 비어서 반경과 무관하게
등록되므로 시험이 되지 않는다.

### 위치 오차 실측 (2026-08-27, 최초)

불을 자로 재서 옮기고 시스템 계산값과 비교했다.

| 자로 잰 실제 이동 | 시스템 계산 | 오차 |
|---|---|---|
| 0.75 m (대각선) | 0.86 m | **+0.11 m (약 15%)** |

**이 값이 `dedup_radius_m` 의 하한을 정한다.** 오차가 ±0.11 m 이면 실제
0.30 m 이동이 0.19~0.41 m 로 읽힌다. 그래서 반경을 0.2~0.3 으로 낮춰
"30 cm 이동도 감지" 를 하려 하면 잡을지 못 잡을지가 복불복이 된다.
현재 0.5 는 실측 오차의 약 4.5배라 안전하다.

`_estimate_position_uncertainty()` 의 placeholder 값 0.15 가 실측 0.11 과
가까운 것도 확인됐다.

### 근본 해결 (미완)

위치 오차는 거리에 비례한다 (`오차 ≈ depth × tan(헤딩오차)`). 그래서 고정
반경이 아니라 **거리 비례 동적 반경**이 맞다. `_estimate_position_uncertainty()`
가 그 자리인데 지금은 `return 0.15` 고정값 placeholder 다. 시간 생기면 여기를
실제로 구현하고 `dedup_radius` 를 이벤트마다 계산할 것.

## 6. 그 밖에 겪은 사고와 현재 방어

| 사고 | 원인 | 방어 |
|---|---|---|
| 핑이 반짝하고 꺼짐 | 검출 직후 그 자리에서 판정 | `left_vantage` (한 번은 벗어나야 함) |
| 카메라가 등 돌린 구간을 "봤다"로 셈 | clear 가 거리만 봄 | `revisit_yaw_tol_deg` + `in_camera_fov()` |
| clear 가 영영 발동 못 함 | `has_left_once` 가 2.0 m 기준이라 순찰 기하상 못 벗어남 | 기준을 0.35 m 로 좁힘 |
| clear 확인이 2.2바퀴나 걸림 | 시간 기준이라 가림 시간보다 길어야 했음 | 위치 기준으로 전환 |
| 저신뢰도 1프레임 오탐이 정지시킴 | confidence 필터 없음 | `min_confidence` 0.5 |
| 맵 밖까지 유령 핑이 찍힘 | depth 상한 없음 (2.5도 헐거웠다) | `max_depth_m` 2.0 |
| 팝업만 뜨고 정지는 안 함 | gate 는 2.5 m 상한, 전송 경로는 상한 없음 | 두 경로가 같은 상한을 쓰게 함 |
| 불 옮겨도 무반응 | 화면좌표 기준 영구 기억 | `yolo_depth_publisher` 의 `reported_tids`/`reported_fallbacks` 제거 |
| **사람이 화면에 한 번 들어오면 불을 영영 못 봄** | person crop 재검출이 `model(crops, classes=[helmet,no_helmet])` 로 부르는데, ultralytics 는 Model 하나가 predictor 하나를 공유하고 kwargs 를 **누적 병합**한다. 그 classes 필터가 메인 추론에 눌러붙어 fire/level 이 전부 걸러졌다 | 메인 추론이 `classes=None`, `conf` 를 **매번 명시**. `test_predictor_args_leak.py` |
| `confidence_threshold` 가 먹은 척만 함 | `predict()` 에 `conf` 를 안 주면 ultralytics 기본 0.25 가 적용된다. `no_helmet`/`fallen_person` 0.15 는 **한 번도 작동한 적이 없었다** | `conf=self._min_conf` 명시 |
| **치워짐이 처음 성공하는 순간 change_point 사망** | `clear_verdict` 가 clear 를 확정하며 `arrived_at` 을 None 으로 되돌리는데, 호출부가 그 값을 덮어쓴 뒤 로그에서 `now_s - ev['arrived_at']` 를 계산 → `TypeError` | 판정 **전에** 값을 붙잡아 둠. `respawn=True` + 배너 + 5초마다 찍는 감시견 |

## 6-1. ★ 증상이 같아도 원인은 인지 단(YOLO)과 판정 단(change_point) 두 곳이다

2026-08-27 에 "불을 봐도 로봇이 안 멈춘다" 를 하루 종일 쫓았는데, **원인이 두 개**
였고 서로 무관했다. 증상이 똑같아서 하나를 고칠 때마다 다른 하나가 남아
"고치면 또 깨지는" 것처럼 보였다. 같은 함정을 다시 밟지 않도록 적어둔다.

**change_point 가 죽으면 겉보기엔 멀쩡하다.** websocket_client 는 원본
`/event_detection/uvd` 도 구독하므로:

| 보이는 것 | 실제 |
|---|---|
| 프론트 팝업 뜸 · 핑 찍힘 | `/uvd` 경로가 살아 있어서 (정상처럼 보임) |
| 로봇이 안 멈춤 | `/map_point` 끊김 → `event_gate_node` 가 아무것도 못 받음 |
| 불을 치워도 핑이 안 지워짐 | `/cleared` 끊김 |

**분기하는 한 줄:**

```bash
ros2 topic info /event_detection/map_point | grep Publisher
#   Publisher count: 0  -> change_point 가 죽었다 (판정 단 문제)
#   Publisher count: 1  -> 살아있다. 인지 단(YOLO 검출)을 볼 것
```

인지 단이 의심되면 **노드 밖에서 같은 영상에 직접 추론**해 비교한다. 노드는
