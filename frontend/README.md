# Frontend — 3D 디지털 트윈 관제 대시보드

스마트 조선소 디지털 트윈 시스템의 웹 관제 대시보드입니다.
브라우저에서 3D 가상 조선소(선박 블록)를 렌더링하고, 서버가 중계하는 AI 감지
이벤트를 받아 Red Alert Ping 점멸·공정률 색상·이벤트 로그로 시각화합니다.

담당: 고명재 (Frontend & 3D Engineer)

## 기술 스택

| 구분 | 기술 |
|---|---|
| UI 프레임워크 | React 19 |
| 3D 렌더링 | Three.js (WebGL) |
| 빌드 도구 | Vite 8 |
| 린터 | Oxlint |

## 구현된 기능 (ShipyardTwinDashboard.jsx 내부 구성 순서)

1. **도메인 상수** — 탐지 클래스별 라벨/심각도, 선박 5구획(S1~S5) 정의
2. **좌표 매핑 레이어** — 서버 좌표(구획 id + 로컬 오프셋) → Three.js 3D 좌표 변환
3. **Three.js 씬 매니저** — 선박 블록 렌더링, Red Alert Ping 점멸, 블록 클릭 픽킹
4. **CCTV 영상 렌더** — 상시 라이브 패널 + Click & View 팝업 (서버 mediamtx WebRTC)
5. **메인 대시보드 UI** — 실시간 위험 요약 / 구획별 공정률 / 이벤트 로그 패널
6. **위치 문구·감지 사진** — 핑을 "S3 왼편"처럼 표기하고, 팝업에 감지 순간 사진을 띄움 (아래 참고)

## 실행 방법

Node.js가 필요합니다 (설치 방법은 루트 `CONTRIBUTING.md` 7번 참고).

```bash
cd frontend

# 1. 패키지 설치 (최초 1회, node_modules 폴더가 생성됨)
npm install

# 2. 개발 서버 실행
npm run dev
```

터미널에 표시되는 주소(기본 http://localhost:5173)를 브라우저로 열면 대시보드가 뜹니다.
현재는 백엔드 없이도 **모의 이벤트(2.2초 간격)** 로 동작하도록 되어 있습니다.

## 백엔드 연동 상태

**실제 백엔드에 붙어 있습니다.** (`USE_REAL_BACKEND = true`, 25행 근처)

- 이벤트는 `ws://${SERVER_HOST}/ws/frontend` 로 실시간 수신합니다
- `connectEventSource()` 는 이제 **`USE_REAL_BACKEND = false` 일 때만** 도는
  mock 피드입니다 — 젯슨 없이 대시보드만 띄워볼 때 씁니다
- 서버 스키마(`event_type`·`confidence`·`map_xy`·`event_id`)를 프론트 내부 표현
  (`cls`·`conf`·`blockId`·`local`)으로 바꾸는 변환은 **onMessage 핸들러 안에서
  이미 하고 있습니다.** `mapXYToPingWorld()` 가 `map_xy` + `ship_pose` 로
  구획과 배 안팎을 판정합니다

> 예전 이 자리에는 "아직 mock 으로만 돌고 있어 스키마 불일치가 문제를 일으키지
> 않는다"는 표가 있었습니다. **더 이상 사실이 아니라 2026-08-28 걷어냈습니다.**
> 거기 적혀 있던 `depth_xyz`·`uwb_xy` 는 v1.6 에서 `map_xy` 로 대체된 옛 키입니다.

정본은 [`docs/interface.md`](../docs/interface.md) 입니다.

## 영상은 중앙 미디어 서버에서 온다

브라우저가 **서버 노트북의 mediamtx** 에 붙습니다
(`DIRECT_CAMERA_URL = "http://192.168.0.5:8889/ugv1"`, 51행 근처).
백엔드(FastAPI)와는 별개 프로세스이고, 백엔드는 영상을 나르지 않습니다.

```
젯슨 ──H.264 1개──▶ mediamtx(192.168.0.5) ──WebRTC──▶ 브라우저 N명
```

> 2026-08-28 에 mediamtx 를 젯슨(192.168.0.6)에서 서버(192.168.0.5)로 옮겼습니다.
> 전에는 젯슨이 시청자마다 스트림을 뿌려서, 탭을 여러 개 열면 로봇이 부담을
> 졌습니다. 지금은 몇 명이 보든 젯슨은 하나만 올립니다.

> **P2P 가 아닙니다.** mediamtx 가 미디어 서버이고 브라우저가 거기 접속하는
> client-server 구조입니다. WebRTC 를 쓸 뿐 양쪽이 대등하지 않습니다.

> **영상이 안 나오면** 대시보드보다 `http://192.168.0.5:8889/ugv1` 을 브라우저로
> 직접 열어봅니다. 거기서도 안 나오면 프론트 문제가 아니라 미디어 서버 쪽입니다
> ([`server/streaming/README.md`](../server/streaming/README.md)).

**왜 이렇게 하나** — 젯슨 6코어에서 Nav2 자율주행·YOLO 추론·영상 송출을 동시에
돌려야 하는데, CPU 가 포화되면 Nav2 의 lifecycle 전환이 타임아웃돼 자율주행이
통째로 실패합니다(실제로 겪었습니다). 그래서 영상 경로에 인코딩을 한 번만 두는
구조를 택했고, 실측으로 영상 전체가 **0.43 코어**입니다.

백엔드가 중계하려면 MJPEG 가 되어 대역폭이 3~5배로 늘고 혼잡 제어가 사라집니다.
WebRTC 는 회선이 밀리면 스스로 화질을 낮춰 버팁니다.

**여전히 단일 LAN 데모 구성입니다.** 관제실이 다른 망에 있으면 접속이 안 됩니다.
외부망 수단이 없어서가 아니라 — ngrok 외부 주소는 있지만 — 데모 버전이라
거기까지 확장하지 않았습니다.

> 예전에 있던 "백엔드 중계(relay) 모드"는 **2026-08-28 삭제했습니다.**
> 젯슨이 그 창구로 프레임을 보낸 적이 한 번도 없어 실제로는 동작하지 않는
> 폴백이었고, 남겨두면 쓸 수 있는 선택지로 오해를 삽니다.
> 자세한 근거는 [`docs/interface.md`](../docs/interface.md) ⑤ 참고.

## 새로고침해도 위험 핑이 남는다 (재접속 복원)

브라우저를 새로고침하면 대시보드가 서버에 다시 접속하는데, 이때 서버가
**아직 살아있는 위험 이벤트**를 다시 보내준다. 그래서 핑이 같은 자리에 다시 뜬다.

복원분에는 `replay: true` 가 붙어 있고, `handleDetectionEvent` 는 이 표시가 있으면
**핑과 블록 강조는 그리되 팝업은 띄우지 않는다.**

- 이미 관제사가 확인한 이벤트일 수 있고
- 살아있는 이벤트가 여러 개면 새로고침할 때마다 팝업이 연달아 떠서 화면을 덮는다
- 대신 `dangerByBlockRef` 기록은 그대로 남기므로, **그 블록을 클릭하면 확인 버튼
  팝업이 뜬다**

### ⚠️ 백엔드를 다시 켜면 이전 핑은 전부 초기화된다

복원 대상은 **백엔드가 켜진 시각 이후에 들어온 이벤트뿐이다.** 서버를 재시작하면
그 전 핑은 사라지고 새로고침해도 다시 뜨지 않는다. 젯슨이 중복 제거 때문에
다시 보내주지 않기 때문이다. **시연 중에는 백엔드를 재시작하지 않는 것이 좋다.**

자세한 근거는 [`backend/README.md`](../backend/README.md) 의
「대시보드 재접속 시 위험 핑 복원」 참고.

## 핑 위치 문구와 감지 순간 사진

### 위치 문구 — "S3" 대신 "S3 왼편"

이벤트 로그와 팝업에 구획 id 만 뜨면 관제사가 어느 쪽으로 가야 할지 알 수 없습니다.
그래서 배 기준 좌우·앞뒤를 붙여 한 줄로 보여줍니다.

| 핑의 위치 | 표기 | 예 |
|---|---|---|
| **배 위**(선체 안) | 구획 + `위` | `S1 위` |
| 배 밖, 앞뒤 범위 안 | 구획 + 좌/우 | `S3 왼편` |
| 배 밖, 앞뒤 끝을 넘어감 | 구획 + 앞/뒤 + 좌/우 | `S1 앞쪽 왼편` |

> ### 배 위에서는 좌/우를 말하지 않습니다
>
> 배 폭이 14cm(반폭 7cm)인데 좌표 오차가 3~5cm 입니다. 갑판 위 대상의 좌/우는
> **센서 정밀도 안쪽**이라 자주 뒤집힙니다 — 실측에서 우현에 놓은 불이 좌현으로
> 읽혔습니다. 틀릴 수 있는 정보를 관제 화면에 쓰느니 안 쓰는 편이 낫습니다.
> 구획(S1~S5)은 한 칸이 15cm 라 오차보다 3배 커서 믿을 수 있습니다.
>
> **배 밖은 반대입니다.** 야드는 넓어서 좌/우가 오차보다 훨씬 크고, 관제사가
> 어느 쪽으로 돌아가야 하는지 알려면 그 정보가 필요하므로 유지합니다.

- 좌우는 **배 자신의 기준**(좌현/우현)입니다. 카메라를 어디서 보든 문구가 바뀌지 않습니다
- ⚠️ **`beam` 양수는 좌현(왼편)입니다.** map 은 오른손 좌표계고 `yaw` 는 +x 기준
  반시계라(interface.md ④), 뱃머리가 +x 를 볼 때 +y 가 왼쪽입니다.
  2026-08-29 이전에는 주석과 표기가 반대로 돼 있어 **화면 문구의 좌/우가
  뒤바뀌어 있었습니다** (3D 핑 위치는 원래 맞았고, 글자만 틀렸습니다)
- **"중앙"은 두지 않습니다.** 배 폭이 14cm뿐이라 중앙이라고 해봐야 좌우 7cm 안이고,
  관제사 입장에서는 어느 쪽으로 갈지 정해주는 편이 낫기 때문입니다
- 계산은 `describePingLocation()` 한 곳에서만 합니다. 서버에서 새로 받는 값은
  없고, 이미 쓰고 있던 `mapXYToShipLocalMeters()` 의 결과를 그대로 씁니다
- 배 위치(`ship_pose`)를 아직 못 받았으면 예전처럼 구획 id 만 나옵니다

### 핑과 구획을 눌렀을 때

| 누른 것 | 나오는 것 |
|---|---|
| **핑 하나** | 그 이벤트 하나의 사진 (옆 핑은 안 끌어온다 — "이거 뭐야?"에 대한 답이므로) |
| **구획** | 그 구획에 걸린 위험 **전부**의 사진을 나란히 |

3D 에서 핑은 구획 메쉬 위에 겹쳐 있는데, 클릭 판정은 **핑을 먼저** 본다.
조준해서 누른 의도는 "이 핑"이지 "이 구획"이 아니기 때문이다.

> 위험 이벤트는 `event_id` 기준으로 보관한다. 예전에는 구획당 한 건만 들고 있어서
> 같은 구획에 불이 둘이면 나중 것이 앞 것을 지웠고, 그래서 스냅샷도 하나만 떴다.

### 구획 색 — 위험(빨강)과 선택(청록)은 별개다

위험 구획은 여러 곳이어도 **전부** 빨갛게 남는다. 그중 하나를 선택하면 더 밝아진다.

위험 구획은 **숨쉬듯 점멸**합니다. 재접속 복원으로 되살아난 위험은 팝업을 띄우지
않기 때문에(새로고침마다 팝업이 연달아 뜨는 것을 막으려고), 화면에 눈길을 끄는
것이 없으면 빨간 구획을 놓치기 쉽습니다. 박자는 핑과 같고, 위험 구획이 여러
곳이면 **함께** 숨쉽니다.

위험이 치워지면(`event_cleared` 또는 "핑 직접 지우기") 원래 색으로 돌아옵니다.
같은 구획에 위험이 여럿이면 **마지막 하나가 없어질 때까지** 빨간 상태를 유지합니다.

> 예전에는 둘이 같은 채널을 써서, 선택 안 된 구획의 밝기가 0 으로 밀렸다.
> 빨간색은 칠해져 있는데 안 보이는 상태라 "마지막 이벤트 하나만 색이 바뀐다"로 보였다.

### 감지 순간 사진

팝업 위쪽에 **그 이벤트가 감지되던 순간의 사진**이 한 장 뜹니다.
아래 영상은 "지금"을 보여주고, 이 사진은 "그때"를 보여줍니다.

- 젯슨 → 백엔드 → 프론트 순서로 오는데, **사진 데이터 자체는 오지 않습니다.**
  백엔드가 파일로 저장해두고 주소(`/snapshots/....jpg`)만 알려줍니다.
  브라우저가 그 주소를 캐시하므로 두 번째부터는 받지 않습니다
- 위험 이벤트가 먼저 오고 사진이 **조금 뒤에** 따로 옵니다. 팝업이 이미 떠 있으면
  그 자리에서 사진 칸이 채워집니다
- **사진이 없어도 화면은 그대로 동작합니다.** 아직 안 왔거나, 구버전 이벤트이거나,
  서버에서 사진이 지워진 경우 그 칸만 조용히 빠집니다
- 새로고침 복원으로 되살아난 핑에도 사진이 함께 옵니다 (같은 코드로 처리됩니다)

> 사진 주소는 `SERVER_HOST` 에서 자동으로 만들어집니다
> (`SNAPSHOT_BASE_URL`). 서버 주소를 바꾸면 영상·이벤트와 함께 따라옵니다.

### 배 위 판정 여유는 비율이 아니라 절대값

`ON_SHIP_SLACK_M = 0.08` (미터). 예전에는 비율(15%)이었는데, 길이(77cm)에는
5.8cm 여유가 붙고 폭(14cm)에는 **1.0cm** 밖에 안 붙었습니다. 측정 흔들림은
방향과 무관하게 비슷한데(중앙값 5cm) 좌우 여유만 그 1/5 이라, **갑판 위에 놓인
불도 절반 넘게 "배 밖"으로 튕겨 야드 바닥에 그려졌습니다.**

여유는 흔들림 중앙값(5cm)보다 넉넉하고 최대값(20cm)보다는 작게 잡습니다.
너무 키우면 이번엔 배 옆 바닥의 불이 갑판 위로 올라옵니다.

### 뱃머리·선미에서 좌우가 눌리지 않게 (`HULL_BEAM_FLOOR`)

핑의 화면 좌우 위치는 **그 지점의 선폭**에 비례합니다. 그런데 뱃머리·선미는
뾰족해서 선폭 계수가 끝에서 `0.03` 까지 떨어집니다. 그대로 곱하면 좌우
오프셋이 통째로 눌려, **끝에 놓인 대상은 좌우가 정확해도 화면에서 가운데로
보입니다.**

하한 `0.35` 를 둡니다. 아주 뾰족한 끝에서는 핑이 선체선을 조금 넘칠 수 있지만,
관제 화면에서는 "선체선 안"보다 "어느 쪽인지"가 더 중요합니다.

### 핑 위치 보정 (`PING_OFFSET_*`)

배 폭이 14cm 인데 객체 좌표 오차는 십수 cm 급이라, 핑이 실제보다 한쪽으로
치우쳐 보일 수 있습니다. 카메라나 젯슨 쪽에서 정밀도를 올리는 것은 비용 대비
효과가 없고, 대시보드는 "어느 구획 어느 쪽"만 맞으면 되므로 여기서 되돌립니다.

**기본값은 0(보정 없음)이고, 값은 추측하지 말고 한 번 재서 넣습니다:**

1. 감지 대상을 **위치를 아는 자리**에 놓는다 — 정중앙일 필요 없음.
   눈대중 중앙보다 물리적 기준선이 정확하다: **좌현(왼쪽)** 옆면에 붙이면 좌우
   참값이 `+0.07`(반폭), 우현이면 `-0.07`, 앞뒤 중앙이면 앞뒤 참값이 `0`
   (모형이 항공모함이라 중앙에 관제탑이 있어 좌우 중앙에는 놓을 수 없다)
2. 로봇이 감지하게 하고 브라우저 콘솔의 `[핑 보정]` 줄을 본다
   ```
   [핑 보정] fire  원본 앞뒤=-0.02 좌우=-0.13  →  표시 앞뒤=-0.02 좌우=-0.13
   ```
3. **보정값 = 참값 − 원본** 을 `PING_OFFSET_FORWARD_M` / `PING_OFFSET_BEAM_M` 에 넣는다
   (우현 옆면에 놓고 원본이 `앞뒤=-0.02 좌우=-0.20` 이었다면
   → 앞뒤 `0-(-0.02)=+0.02`, 좌우 `-0.07-(-0.20)=+0.13`)
4. 다시 감지시켜 **표시** 값이 참값 근처로 오는지 확인한다

**2026-08-29 실측 결과** (젯슨이 같은 불 97건을 군집 분석):

| 불 | 참값 (앞뒤, 좌우) | 군집 중심 | 오차 |
|---|---|---|---|
| 뱃머리 좌현 | `+0.35, +0.03` | `+0.331, +0.002` | `-0.019, -0.028` |
| 선미 우현 | `-0.35, -0.03` | `-0.399, +0.022` | `-0.049, +0.052` |

- **앞뒤**: 둘 다 음수(선미 쪽으로 밀림) → 계통 편향으로 보고 `+0.034` 적용
- **좌우**: `-0.028` 과 `+0.052` 로 **부호가 반대** → 편향이라는 근거가 없어 **0 유지**.
  평균을 넣으면 잡음에 맞추는 꼴입니다

> ⚠️ **군집 중심은 이미 2~5cm 로 정확합니다.** 화면에서 핑이 엉뚱한 곳에 찍히는
> 주된 원인은 편향이 아니라 **건별 흩어짐**(중앙값 0.05m, 최대 0.20m)입니다.
> 이벤트는 군집 평균이 아니라 **한 번의 검출**로 등록되므로, 그 한 번이 어디로
> 튀었느냐가 그대로 핑 위치가 됩니다. 상수 보정으로 고칠 수 있는 범위는
> 여기까지입니다.

> ⚠️ **좌/우 표기는 이 모형에서 원래 불안정합니다.** 배 폭이 14cm(반폭 7cm)인데
> 측정 오차가 3~5cm 라, 중심선 가까이 놓인 대상은 좌우가 뒤집혀 읽힐 수 있습니다.
> 시연에서 좌/우를 확실히 보여주려면 대상을 **가장자리에 붙여** 놓으세요.

## 로봇 연결 상태

상단바에 **항상 보이는 배지**가 있습니다. 팝업의 확인을 눌러 닫았어도 지금
상태는 언제든 여기서 볼 수 있습니다.

| 배지 | 뜻 |
|---|---|
| `서버 연결됨` / `서버 끊김` | 이 대시보드와 백엔드 사이 |
| `로봇 연결됨` / `로봇 끊김` | 백엔드와 젯슨 사이 |
| `로봇 연결됨 (준비 중…)` | 소켓은 붙었지만 AMCL·Nav2 가 아직 — **관제는 아직 안 됨** |
| `로봇 준비 완료` | 자율주행·감지가 모두 준비됨 (`jetson_ready` 수신) |
| `로봇 상태 확인 중` | 아직 서버로부터 상태를 못 받음 (구버전 백엔드이거나 접속 직후) |

> ### 연결됨 ≠ 준비됨
>
> 젯슨의 `websocket_client` 는 로컬라이제이션에서 뜨는데 AMCL·Nav2 는 그보다 늦게
> 뜹니다. 그 사이 소켓은 살아 있어 "연결됨" 이 뜨지만 **로봇은 순찰도 못 하고
> 이벤트도 못 잡습니다.** 그래서 2단계로 나눕니다.
>
> 준비 완료 팝업이 뜨면 핑·상태가 이미 다 도착한 뒤라 **수동 새로고침이 필요
> 없습니다.** 젯슨이 재연결 때 다시 보내므로 팝업은 한 연결에 한 번만 띄웁니다.

**둘은 다른 것입니다.** 서버는 붙어 있는데 로봇만 꺼져 있는 상황이 흔하므로
배지를 따로 뒀습니다. 로봇 끊김은 빨강이 아니라 **노랑**입니다 — 빨강은 위험
이벤트 색이라, 연결 문제와 화재를 같은 색으로 두면 헷갈립니다.

## 배에서 너무 먼 검출은 버린다 (`MAX_EVENT_DIST_FROM_SHIP_M`)

로봇의 카메라는 순찰 원 **안쪽(배 쪽)** 을 봅니다. 그러니 배에서 한참 떨어진
곳의 화재는 원리상 나올 수 없습니다. 그런데 실제로 벽 근처의 무언가를 불로
오인한 검출이 유령 핑으로 떴습니다.

**실측** (2026-08-29 02~04시, 화재 15건):

| | 배 중심에서의 거리 |
|---|---|
| 진짜 이벤트 11건 | 최대 **0.84 m** |
| 유령 4건 | 최소 **1.60 m** |

사이에 0.76 m 의 빈 구간이 있어 `1.2 m` 로 자릅니다.

> ### 젯슨의 `max_depth_m` 과 혼동하지 마세요 — 재는 것이 다릅니다
>
> | | 재는 거리 |
> |---|---|
> | `max_depth_m` (젯슨) | 로봇 ~ 대상 |
> | 여기 / `max_dist_from_ship_m` (젯슨) | **배 중심** ~ 대상 |
>
> 유령 4건을 실측하니 **로봇에서 약 1 m** 였습니다. depth 는 정상이었고
> `max_depth_m 2.0` 을 정당하게 통과했습니다. 유령은 "멀리 있는 것"이 아니라
> **"로봇 옆인데 배 반대편에 있는 것"** 이라, 로봇 기준 거리로는 원리적으로
> 걸러낼 수 없습니다.
>
> 2026-08-29 젯슨 실측: `fire` 등록 181건 중 **49건(27%)** 이 배에서 1.2m 초과.
> 그동안 프론트만 막고 있었고 젯슨은 서버로 다 보내고 로봇도 다 멈췄습니다.
>
> 지금은 젯슨에도 같은 게이트가 있습니다(`max_dist_from_ship_m`, 커밋 921314a).
> **거기가 1차 방어선이고 여기는 마지막 그물입니다.** 두 값은 같은 것을 재므로
> 한쪽만 바꾸면 조용히 어긋납니다.
>
> 배 위치를 모르면 거르지 않습니다(fail open) — 젯슨도 같은 정책입니다.
> 모르는 상태에서 막으면 진짜 이벤트까지 사라집니다.
>
> ⚠️ **순찰 반경을 크게 바꾸면 이 값도 올려야 합니다.** 안 그러면 진짜 이벤트가
> 사라집니다 — 그래서 걸러낼 때 콘솔에 `[이벤트 걸러냄]` 으로 반드시 남깁니다.

## 서버가 끊겨도 로봇은 제자리에 있는다

예전에는 "진짜 좌표를 아직 못 받았으면" 장식용 자동 순찰 애니메이션이 돌았습니다.
그래서 **서버가 끊긴 상태로 새로고침하면 로봇이 제멋대로 사각형을 그리며 돌았습니다.**
관제 화면에서 그것은 거짓 정보입니다 — 실제 로봇은 서 있는데 화면만 순찰합니다.

이제 가짜 순찰은 **mock 모드(`USE_REAL_BACKEND = false`)에서만** 돕니다.
진짜 연동 중에는 좌표가 없으면 **마지막으로 받은 위치에 그대로** 있습니다.

## 접근 암호 (서버가 걸었을 때만)

서버 `.env` 에 `DASHBOARD_PASSWORD` 가 있으면 첫 진입에 로그인 화면이 뜹니다.
**없으면 로그인 화면도 없고 지금까지와 똑같이 동작합니다** — 팀원이 각자
노트북에서 받아 그대로 실행할 수 있어야 하기 때문입니다.

- **로그아웃 버튼**이 상단바에 있습니다(암호를 건 서버에서만 보입니다).
  누르지 않는 한 브라우저를 닫았다 켜도 그대로 들어가지고, 누르면 다음 접속에
  암호를 다시 칩니다 — 매번 치는 번거로움과, 자리를 뜰 때 잠그는 것 사이의 타협입니다
- 토큰은 `localStorage` 에 둡니다. `sessionStorage` 는 **탭마다 따로**라 창을
  하나 더 열 때마다 다시 로그인해야 했습니다. 브라우저를 닫아도 남으므로, 화면을
  잠그고 싶으면 브라우저 데이터를 지우거나 **암호를 바꿉니다**(토큰이 암호에서
  유도되므로 전부 무효가 됩니다)
- 토큰이 거부되면(401) 토큰을 버리고 로그인 화면으로 되돌아갑니다 — 재접속만
  반복하는 상태에 갇히지 않게 하기 위함입니다
- **서버에 못 붙어도 대시보드는 띄웁니다.** 여기서 막으면 서버가 꺼졌을 때
  빈 화면만 남아 무슨 일인지 알 수 없습니다. "서버와의 연결이 끊겼습니다" 팝업으로
  알려주는 편이 낫습니다

## 구획을 눌렀을 때

**위험이 있는 구획만** 팝업이 열립니다. 예전에는 빈 구획을 눌러도 CCTV 팝업이
떠서 "정상 — 활성 경보 없음" 만 보여줬는데, 실시간 영상은 화면 아래에 늘 흐르고
있어 보여줄 것이 없었고 3D 를 돌리려다 잘못 눌러 뜨는 일이 잦았습니다.

**공정률 목록은 이제 누를 수 없습니다.** 대신 완성된 시각을 그 자리에 적습니다 —
공정률을 보다가 영상이 뜨는 것은 엉뚱했고, 실제로 궁금한 것은 "언제 완성됐나"
였기 때문입니다.

## 위험 / 경고 칸을 눌러 걸러 보기

상단 요약의 **위험**·**경고** 칸을 누르면 아래 로그가 그 종류만 남습니다.
다시 누르거나 `전체 보기` 를 누르면 해제됩니다.

| 칸 | 포함되는 것 |
|---|---|
| 위험 | 화재, 작업자 쓰러짐 |
| 경고 | 안전모 미착용, 선박 결함 |

> **"정상" 칸은 뺐습니다.** 아무 일도 없다는 것을 숫자로 세는 칸이라 관제사가 볼
> 이유가 없고, 늘 0 이라 화면만 차지했습니다.

## [🎬 녹화] — 시작/정지 · 삭제 · 지난 영상 보기

상단바 버튼. 세 가지를 한 화면에서 합니다.

| | |
|---|---|
| **시작 / 정지** | mediamtx 의 녹화를 실시간으로 켜고 끕니다 (재시작 불필요) |
| **영상 삭제** | ⚠️ **서버 노트북의 영상 파일이 실제로 지워집니다.** 되돌릴 수 없습니다 |
| **선택 삭제** | 오래된 것부터 N개. 조각이 약 1분이라 **개수가 곧 분**입니다 |
| **지난 영상 보기** | 타임라인을 누르거나 시각을 입력해 그 시점부터 재생 |

### 타임라인

녹화 조각을 하나의 시간축에 깔아 보여줍니다. **누른 지점부터 재생**되고, 빨간
선이 현재 재생 위치입니다. 조각이 없는 구간은 빈칸으로 보입니다 — 그때는 녹화가
꺼져 있었거나 스트림이 끊겼던 때입니다.

시각을 글로 넣을 수도 있습니다. **이벤트 로그의 시각을 그대로 옮겨 적는 것이
가장 흔한 쓰임**입니다.

```
07:12:30                 오늘(정확히는 첫 조각의 날짜) 기준
2026-08-29 07:12:30      날짜까지
```

한 번에 볼 길이는 15초 / 1분 / 5분 중에 고릅니다.

### 얼마나 지울지 고르기

조각 하나가 대략 **1분**입니다. 그래서 개수로 고르게 했습니다 — 시각 범위를
지정하는 것보다 단순하고, 실제로 하고 싶은 일("앞쪽 오래된 것 좀 지우기")에
바로 맞습니다. `30` 을 넣으면 오래된 것부터 약 30분치가 지워집니다.

`전부` 는 말 그대로 다 지웁니다. 그와 별개로 **2시간이 지난 것은 mediamtx 가
알아서 지웁니다**(`recordDeleteAfter: 2h`) — 그냥 두어도 무한히 쌓이지 않습니다.

> **삭제할 때 지금 녹화 중인 조각 하나는 남깁니다.** mediamtx 가 열어둔 채 쓰고
> 있는 파일이라, 지워도 공간이 안 돌아오고 그 조각만 깨집니다. 다음 조각으로
> 넘어가면 보관 기간에 걸려 알아서 사라집니다.

> **영상이 안 나오면** 재생 API 포트(9996)가 방화벽에 열려 있는지 보세요.
> `sudo bash server/streaming/setup-firewall.sh`

## [📚 지난 기록] — 날짜별 조회

상단바 오른쪽 버튼. 날짜를 골라 그날의 위험 이벤트를 시간순으로 봅니다.
감지 순간 사진, 감지 시각, 치워진 시각이 함께 나옵니다. 사진을 누르면 크게 봅니다.

실시간 관제와 목적이 다릅니다 — 여기는 **"그때 무슨 일이 있었나"** 를 되짚는
화면이라, 지금 살아있는지와 무관하게 그날 있었던 것을 전부 보여줍니다.

| API | 주는 것 |
|---|---|
| `GET /api/event-days` | 이벤트가 있었던 날짜와 건수 (최신순 60일) |
| `GET /api/events?date=YYYY-MM-DD` | 그날의 위험 이벤트 + `image_url` + `cleared_at` |

- 날짜 선택기에는 **이벤트가 있었던 날만** 나옵니다. 빈 날짜를 고르고 "왜 아무것도
  없지" 하는 일을 없애기 위함입니다
- 같은 `event_id` 가 여러 번 기록됐어도(재통보 등) 한 번만 보여줍니다
- `치워짐 기록 없음` 은 그 이벤트에 `event_cleared` 가 오지 않았다는 뜻입니다

## [🧹 초기화] 버튼

이벤트 로그 패널 오른쪽 위에 있습니다. 유령 핑이나 엉뚱한 자리의 이벤트가
생겼을 때 프로세스를 껐다 켜지 않고 정리합니다.

누르면 `{"event_type":"reset_events"}` 를 보내고, 화면·서버·로봇이 함께 비워집니다.

| | |
|---|---|
| 화면 | 핑 전부 제거, 구획 위험 표시 해제, 로그·요약 0 |
| 서버 | 복원 기준선을 지금으로 밀어 이후 새로고침에도 안 돌아옴 |
| 로봇 | `change_point` 보고 이력과 재통보 거울을 비움 |

> ### 되돌릴 수 없고, 누른 뒤에는 로봇이 다시 멈춥니다
>
> 기억을 비웠으므로 같은 자리의 불을 **새 이벤트로 다시 보고하고 로봇도 다시
> 멈춥니다.** 그것이 정상 동작입니다 — 안전한 방향의 실수라(놓치는 것이 아니라
> 한 번 더 알림) 잘못 눌러도 위험하지는 않습니다. 다만 모르고 누르면 당황하므로
> 확인 대화상자를 띄웁니다.
>
> **DB 기록은 지우지 않습니다.** 기록은 증빙이고, "안 보이게 하는 것"과 "지우는
> 것"은 다릅니다.

## 서버가 끊기면 스스로 다시 붙는다

`connectRealEventSource` 가 **2초마다 재시도**합니다. 백엔드를 다시 켜면
새로고침 없이 대시보드가 알아서 붙습니다.

> ### 나간 것은 알 수 있지만, 돌아온 것은 두드려봐야 압니다
>
> | | 어떻게 아나 |
> |---|---|
> | 서버가 **나갔는지** | 소켓의 `onclose` 가 즉시 알려줍니다 |
> | 서버가 **돌아왔는지** | 가만히 있으면 모릅니다. **새 연결을 시도해야만** 압니다 |
>
> 끊긴 소켓은 되살아나지 않습니다. 2026-08-29 이전에는 재시도가 없어서,
> 백엔드를 다시 켜도 대시보드가 영영 다시 붙지 않았습니다 — 사람이 새로고침해야
> 데이터가 들어왔고, "서버와 재연결되었습니다" 팝업도 뜨지 않았습니다
> (재연결 자체가 일어나지 않았으므로).

간격은 고정 2초입니다. 지수 백오프를 쓰지 않는 이유는, 같은 공유기 안의 서버라
몇 초 안에 돌아오는 것이 보통이고, 백오프가 길어지면 시연 중에 "서버는 켰는데
화면이 한참 안 돌아오는" 상황이 되기 때문입니다.

## 연결이 끊기면 알려준다 (로봇 · 서버 각각)

> ### 새로고침을 제안하는 팝업은 **하나뿐**입니다 — "로봇 준비 완료"
>
> 예전에는 서버 재연결 팝업도 새로고침을 걸어서, 서버와 로봇을 차례로 켜면
> 확인을 두 번 눌러야 했고 새로고침 뒤에 서버 팝업이 다시 뜨기도 했습니다.
>
> 지금은 이렇게 흐릅니다:
>
> | 순서 | 팝업 | 확인을 누르면 |
> |---|---|---|
> | 서버 붙음 | "서버와 재연결되었습니다" | 닫기만 |
> | 로봇 붙음 | "로봇과 연결되었습니다 (아직 준비 중)" | 닫기만 — **서버 팝업은 자동으로 내려감** |
> | 준비 끝 | "로봇 준비 완료" | **화면을 새로 불러옴** |
>
> 확인을 안 눌러도 다음 단계가 오면 앞 팝업은 알아서 내려갑니다.
>
> ### 새로고침을 안 해도 화면이 맞습니다
>
> 서버에 **다시 붙는 순간 화면의 위험을 비우고**, 서버가 보내주는 "지금 살아있는
> 위험" 으로 다시 채웁니다. 그래서 화면은 항상 서버와 같습니다.
>
> 예전에는 옛 핑을 아무도 지우지 않아, 서버가 꺼져 있는 동안 치워진 위험이
> 화면에 계속 남았습니다. 새로고침을 해야만 진실과 맞았고, 그래서 팝업마다
> 새로고침을 걸어야 했습니다. 이제는 필요 없습니다.

**로봇**과 **서버**는 다른 사건이라 팝업 슬롯을 따로 둡니다. 동시에 끊기면
두 장이 **나란히** 뜹니다 — 로봇 팝업을 밀어내지 않아야 관제사가 무엇 때문에
무엇이 멈췄는지 압니다. 슬롯 안에서는 최신 상태가 이깁니다.

| 대상 | 상태 | 문구 |
|---|---|---|
| 로봇 | 끊김 | 로봇과의 연결이 끊겼습니다 / 로봇과 재연결될 때까지 실시간 순찰 정보 관제가 제한됩니다 / 이미 감지된 핑과 로봇의 마지막 위치는 화면에 그대로 남아 있습니다 |
| 로봇 | 재연결 | 로봇과 재연결되었습니다 / 실시간 순찰 정보 관제를 재개합니다 |
| 서버 | 끊김 | 서버와의 연결이 끊겼습니다 / 서버와 재연결될 때까지 … / 이미 감지된 핑과 로봇의 마지막 위치는 … |
| 서버 | 재연결 **+ 로봇도 연결** | 서버와 재연결되었습니다 / 실시간 순찰 정보 관제를 재개합니다 |
| 서버 | 재연결 **but 로봇 미연결** | 서버와 재연결되었습니다 / 다만 로봇이 아직 연결되지 않았습니다 / 로봇이 연결된 후에 실시간 순찰 정보 관제가 가능합니다 |

- **서버가 끊기면 로봇 상태를 "확인 중"으로 되돌립니다.** 로봇 상태는 서버가
  알려주는 것이라, 서버가 끊긴 뒤의 "로봇 연결됨"은 지난 정보입니다
- 배경을 눌러도 안 닫힙니다. 놓치면 안 되는 내용이라 **확인**을 눌러야 합니다

- **이미 감지된 위험 핑은 그대로 남습니다.** 로봇이 꺼진 것과 위험이 사라진 것은
  다릅니다. 핑은 `event_cleared` 나 "핑 직접 지우기" 로만 없어집니다
- 상태가 **바뀔 때만** 뜹니다. 단, 대시보드를 여는 순간 이미 끊겨 있으면 그때도
  알려줍니다 (화면이 평소와 똑같아 보여서 모르고 지나치기 쉬우므로)
- 확인을 안 눌러 팝업이 떠 있는 채로 상태가 또 바뀌면 **최신 상태가 이깁니다** —
  옛 팝업이 자동으로 닫히고 새 팝업으로 바뀝니다
- **재연결 팝업의 확인을 누르면 화면을 새로 불러옵니다.** 단 서버만 붙고 로봇이
  아직이면 새로 불러오지 않습니다 — 가져올 최신 정보가 없기 때문입니다. 확인만 누르고 최신
  정보를 보려고 또 새로고침하는 수고를 없애기 위함입니다. 새로고침 뒤 첫
  `jetson_status` 는 "연결됨" 이라 팝업이 다시 뜨지 않습니다 — 무한 반복이
  생기지 않습니다. 끊김 팝업은 닫기만 합니다(새로 불러올 것이 없으므로)
- 문구는 언제나 **"재연결"** 입니다. 로봇이 정말 처음 켜지는 순간은 현장에 처음
  들어온 그때뿐이고, 그 외에는 늘 이전 세션의 기억을 들고 다시 붙는 것이라
  "재연결"이 사실에 맞습니다
